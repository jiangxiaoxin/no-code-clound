## 1. 一句话说清

普通表单：人填完点保存，数据立刻就是正式数据，谁有数据管理权限就能改、能删。

**流程表单**：人填完点「提交」，数据先进入审批。当前节点的审批人通过或驳回后，才走到下一节点或结束。**没走完的数据不能当正式业务数据随便改。** 通过之后，这条数据才能被别的表的关联数据、关联子表单当作正式记录挑到。下拉单选「其他表数据」取的是字段值不是资格，和现在一样不过滤流程状态。

一张表单是不是流程表单，不看调色板有没有新控件，看它**建表时选的类型**（普通表单 / 流程表单）。建错成普通表单的，可以以后转成流程表单；**流程表单不能转回普通表单**（§4.2）。

流程表单**必须先有已发布的流程才能填报**：只画了字段、没配流程就点提交，提示「这张表单还没有配置流程」，**一条数据都不写**。正因为这样，流程表单上不会出现「绑流程之前就存在的数据」——所有数据要么是走完审批的，要么是明确记为已通过的（转换时回填 §4.2、停用期间保存 §4.3，筛选规则见 §15.2）。

## 2. 贯穿全文的例子

准备一张 **请假单**（和现有「添加数据 / 数据管理」同一套表单，只是多绑了流程）。

| 字段标题 | 调色板控件 |
|---|---|
| 请假人 | 人员单选 `member` |
| 请假类型 | 下拉单选框 `select`（事假 / 病假） |
| 开始日期 | 日期选择 `date` |
| 结束日期 | 日期选择 `date` |
| 事由 | 多行文本 `textarea` |

流程在 **流程设计** 画布上画出来（不是一张从上到下的清单）：

```text
              开始
               │
            【分支】请假类型
           ／事假        ＼病假（否则也可走这边）
    部门审批                    │
    （角色：部门经理，或签）     │
           ＼                  ／
              人事备案（指定人员：张三、李四，会签）
               │
              结束
```

于是：

- 员工打开【请假单】的【添加数据】，填完点【提交】。系统从「开始」顺着连线走：先到分支，看这条数据的「请假类型」。
- **事假**：进入「部门审批」（**或签**）。部门经理角色下的人各自有一条待办；张三、李四还没有。某位经理点「通过」后，未处理的经理待办取消，待办转到「人事备案」。
- **病假**：跳过部门审批，直接到「人事备案」。
- **人事备案**配了张三、李四且为 **会签**：两人都有一条待办。张三先通过，流程仍停在人事备案，等李四；李四也通过后才到结束。若张三驳回，李四的待办取消，整单已驳回。
- 流程走到结束，这条请假变成「已通过」。人事表如果用关联数据指向请假单，现在可以选到它。
- 若当前审批人点「驳回」并写原因：状态变成「已驳回」，发起人改内容再提交，还是**同一条数据**。再次提交时**从开始重新沿连线走**（类型若改成病假，就不再进部门审批）。

下文凡写【请假单】都指这个例子。应用名叫【人事】。

**用词固定（界面上有的字就用这些，不要换）**

| 指什么 | 一律写 |
|---|---|
| 工作台两个页签 | 【添加数据】、【数据管理】。不要写成「添加」 |
| 【数据管理】工具栏按钮 | 【新增】、【编辑】、【删除】（和【表单发布】开关同一套字） |
| 流程填报底部 | 【保存草稿】、【提交】、【再次提交】；流程关掉后回到【保存】 |
| 审批 / 发起 | 【通过】、【驳回】、【撤回】、【重试】 |
| 首页四个入口 | 【我的应用】、【我的待办】、【我发起的】、【我处理的】 |
| 设计顶栏 | 【表单设计】、【流程设计】、【表单发布】、【数据管理】 |
| 表单树菜单 | 【转为流程表单】。没有「转为普通表单」 |
| 本例的应用和表 | 应用【人事】，表【请假单】。不要写成「请假单表单」「请假表」 |

验收步骤里，表名、按钮名、点的动作用【】标出。

## 3. 和现有能力怎么区分

| 人在做什么 | 普通表单（现在） | 流程表单（本文） |
|---|---|---|
| 新建表单时 | 只填名称 | 名称下面多一个**表单类型**单选，选定后顶栏才有「流程设计」页签（§4.1） |
| 还没配流程就去填 | 不存在这种情况 | **不能填**：顶部常驻提示，点保存草稿 / 提交都拦，服务端也不写库（§4.1） |
| 工作台「添加数据」 | 填完点保存，立刻正式入库 | 可「保存草稿」或「提交」。提交才进审批 |
| 数据管理里改一行 | 编辑抽屉或单元格内联编辑 | **审批中不能当普通数据改**；已通过后若发布页「编辑」开着，只能在数据管理里改，改完提交后重新走审批（见 §11） |
| 谁能看见这条 | 能进这张表数据管理的人 | 数据管理仍给能进该表的人看，并带流程状态。另外：发起人在首页「我发起的」看自己的；当前审批人在首页「我的待办」看自己的；批过的人在首页「我处理的」再看。这三处都不要求能进对应应用 |
| 关联数据 / 选择数据去挑这条 | 保存后就能挑 | **只有已通过**才能被别的表当正式数据挑到（草稿、审批中、已驳回都不出现在选记录弹窗里） |

流程表单**不是**调色板新控件，也不改现有字段 `type`。请假类型、日期、人员选择怎么配，仍按各自规格。

## 4. 一张表单怎么变成流程表单

表单设计顶栏现在是：表单设计 / 表单发布 / 数据管理。

**流程表单多一个页签：流程设计**，放在「表单设计」和「表单发布」之间。普通表单顶栏仍是三个页签，看不到流程设计。能进表单设计的人就能进流程设计（和现在谁能保存字段一致，不另做一套权限；按权限规格 §6.3 即所有者或配置名单上的人）。

### 4.1 建表时选类型

应用工作台左侧「新建 → 新建表单」，现在弹的框里只有一个「名称」。在名称下面加一个**表单类型**单选：

- **普通表单**（默认）：填完点保存就是正式数据，和现在完全一样。
- **流程表单**：填完点提交进入审批，要有已发布的流程才能填。

每个选项后面带一句上面的说明，别让人靠猜。类型存到表单配置上（§15.1），**判定一张表是不是流程表单就看这个类型，不看它有没有已发布流程**——否则「还没配流程的流程表单」会被当成普通表单，数据就直接落库了。

**流程表单还没有已发布流程时，不能填报**：

- 工作台「添加数据」能打开（人要知道这张表存在、长什么样），但页面顶部常驻一条提示「这张表单还没有配置流程，暂时不能填报」，别等人填完一屏才拦。
- 底部「保存草稿」和「提交」点了都提示「这张表单还没有配置流程」，**服务端同样拦，一条数据都不写**。
- 草稿也不让存：草稿要落库，落了库就是一条没有实例、没有流程状态的数据，正是本节要消灭的东西；而且没有流程，这条草稿永远也交不出去。
- 【数据管理】里的【新增】同样拦。

### 4.2 转换（只允许普通 → 流程）

入口在左侧表单树的节点菜单里（现有「编辑表单 / 修改名称 / 删除表单」旁边）：**普通表单**上加一项**转为流程表单**。只有所有者和配置名单上的人能点。

**流程表单上没有「转为普通表单」。** 建错了只能删掉这张表再建。直接调转换接口把 `formKind` 改回 `normal` 也要拒绝。

**普通 → 流程**

- 转换时把这张表**已有的记录一次性回填** `workflowStatus = 'approved'`：它们是当普通数据正常填进去的正式数据，转成流程表单后必须还能被别的表挑到（§15.2），否则用户看见的是功能倒退。
- 只写**还没有这个键**的记录，已有的不动。
- 大表要分批更新，别一条语句锁住整张集合。
- 回填不建流程实例。这些数据在详情抽屉的流程进度区显示「转为流程表单之前保存，没有审批记录」，不要画一个空的小流程图让人以为出错了。
- 转完立刻按 §4.1 生效：没发布流程之前不能填。
- **不改** Mongo 里的 `data`，只改表单类型、按需回填状态。

### 4.3 发布与启用开关

**一张表同一时刻最多一份流程配置，发布成功的那份就是正在启用的。** 流程可以改、再发布，成为新版本（§13）。**点「发布」成功后自动启用**，不用再去拨开关。顶栏「保存」只把画布存成草稿，不启用、不影响正在跑的单。

**关掉「启用流程」**（流程设计页一个开关）后：

- 新数据按普通表单保存：底部回到「保存」，没有草稿 / 提交，点保存直接入库，**同时写 `workflowStatus = 'approved'`**，不建实例。这样重新启用后，这批数据在选记录弹窗里照样能挑到，不会凭空消失。
- 数据管理的流程状态列显示「已通过」，详情里注明「流程停用期间保存，没有审批记录」。
- 已经在走的审批继续按**当时那个版本**走完，不中断、不改节点。

**关掉启用期间，三个待办入口必须照常工作**：首页和应用内左侧的「我的待办 / 我发起的 / 我处理的」仍要列出这张表的在途单据，否则审批人找不到入口，单据永远走不完。所以入口的显隐、计数的统计，判定依据是「当前用户有没有未完成的实例或待办」，**不是**「这张表的流程有没有启用」。

这样一来，流程表单上的每一条记录都带 `workflowStatus`：要么走完审批，要么转换时回填，要么停用期间保存时直接写上。**不存在「没有流程状态」的记录**，§15.2 的筛选规则因此只有一条，不用为缺键开特例。

## 5. 流程设计页长什么样

流程必须在前端 **画布设计器** 里配：左侧拖节点、中间连线、点节点或点线出右侧属性。不能改成「只上移下移的清单」——清单画不出分支。

页面结构对齐表单设计：左（节点）+ 中（画布）+ 右（属性）。顶栏是保存草稿、发布、启用流程。

实现上画布用 **LogicFlow 2.x**（安装时取当时的最新 2.x，不要锁死某个 patch）。审批 / 分支 / 结束用官方 **`@logicflow/vue-node-registry`** 把 Vue 单文件组件注册成节点，节点里面可以用 Element Plus。左侧拖拽、右侧属性、顶栏按钮仍是普通 Vue + Element Plus，不要整页都塞进画布。这是二维连线，Flex 做不了，属于现有「优先 Flex」规则的例外。

存库仍是本文的 `nodes` + `edges`（含坐标）。打开设计器时转成 LogicFlow 的图数据；保存时再转回，不要把 LogicFlow 内部字段原样当产品协议。抽屉里的只读小流程图可以再用同一个库只读渲染，或按快照自己画，不要另引第三套画布。

### 5.1 左侧：可拖的节点

| 名称 | 拖上去干什么 |
|---|---|
| 审批 | 要人处理的一步 |
| 分支 | 按表单字段走不同连线（菱形） |
| 结束 | 流程到此通过 |

**开始** 不进左侧：新建流程时画布上已经有一个开始，**只能有一个，不能删、不能再拖第二个**。

从左侧拖到画布空白处落下即新增；落到已有节点上不合并。节点可拖动位置，位置随流程草稿一起保存，刷新画布还在原处。

### 5.2 中间：画布和连线

- 每个节点有出线点、入线点。按住出线点拖到另一个节点的入线点，松开即连上。
- 连线可以点选、删除（Delete 或线上的删除）。
- 点节点：右侧是该节点属性。点连线：右侧是这条线的条件（见 §5.4）。点画布空白：右侧提示「选择一个节点或一条连线」。
- 画布支持平移、滚轮缩放；提供「适应画布」。
- **开始** 必须有且仅有一条出线。
- **审批** 必须有一条出线（指向下一个审批、分支或结束）。
- **分支** 至少两条出线：其中恰好一条标成「其他情况」，其余每条都要配条件。
- **结束** 不能有出线，可以有多条入线（几条支路汇到同一个结束）。
- 允许有多个结束（都表示「已通过」）。驳回不靠连到结束，靠审批人点「驳回」。
- 本期 **不允许环**（连回去形成圈）。发布时若从某点能沿连线走回自己，提示「流程不能绕回已经走过的节点」。
- 本期 **不允许并行**：同一时刻只在一个审批节点等人。两条出线是「只走其中一条」，不是两条同时批。不要做「同时发给经理和人事」。

没连线的节点、从开始走不到的节点、走到尽头不是结束的节点，发布时分别提示，见 §5.6。

### 5.3 右侧：节点属性

**审批节点**（点审批块）：

1. **节点名称**：文本，必填。默认「审批1」「审批2」。
2. **审批人**（必配，见 §7）。
3. **多人审批方式**（单选，默认 **或签**）：
   - **或签**：名单里**任一人**点「通过」，本节点通过，其余人的待办取消；**任一人**点「驳回」，本节点驳回，其余待办取消。
   - **会签**：名单里**每个人都必须**点「通过」，本节点才通过；**任一人**点「驳回」，本节点驳回，其余待办取消。还有人未批时，已批的人卡片从「我的待办」进「我处理的」，流程仍停在本节点，不往下走。
   - 只有一名审批人时，两种模式效果相同。
   - 存库字段 `signMode`：`any` = 或签，`all` = 会签。
4. **本节点字段权限**（见 §12）：每个主表字段（含标签页里的）可选「可编辑 / 只读 / 隐藏」。默认全部只读。发起填写不看这张表。
5. **审批意见**：通过时「选填 / 必填」，默认选填；驳回时固定必填。

**分支节点**（点菱形）：

1. **节点名称**：默认「分支」，可改成「按请假类型」方便认。
2. 不配审批人、不配字段权限。分支只负责选下一条线，不派人、不停留。

**开始 / 结束**：名称固定，右侧只说明「提交后从这里出发 / 走到这里即已通过」，没有审批人。

### 5.4 右侧：连线条件

点的是线，不是节点。

- **从开始、审批出来的那一条线**：不用配条件（它们各只有一条出线）。右侧显示「从「部门审批」到「人事备案」」，可改线上的短标题（画布上沿线显示，如「通过后」），可不填。
- **从分支出来的线**：
  - 必须指定：要么是 **其他情况**（本分支有且仅有一条），要么是 **满足以下条件**。
  - 条件配法和表单里下拉「选项过滤」同一套操作习惯：可多条；多条之间选「全部满足」或「任一满足」。
  - 一行：左边选**当前表单字段**（主表，含标签页；不要子表列）→ 中间选关系 → 右侧自定义值或当前表单另一个同类型字段。
  - 字段类型和关系对齐现有过滤：文本（等于 / 不等于 / 包含 / 为空…）、数字、日期、单选/下拉、人员/部门（等于、为空）。本期不做「动态相对日期」那种复杂项，够用请假类型、天数即可。
  - 线上显示条件摘要，如「请假类型 = 事假」；「其他情况」就显示这三个字。

运行时：按画布上**出线的顺序**（右侧可「上移 / 下移」调整判断顺序）一条一条看，**第一条满足的就走**，都不满足走「其他情况」。不要两条都走。

条件里用到的字段被表单设计删掉：发布时提示「分支「按请假类型」的连线用了已删除的字段」；已发布的旧版本实例仍按快照里的条件算，字段没值就当不满足，落到「其他情况」。

### 5.5 顶部操作

- **保存草稿**：只存流程定义（节点、线、坐标），**不启用**。**不影响这张表能不能填**——能不能填看的是「有没有已发布版本」（§4.1），存了草稿但没发布，工作台照样拦住不让填。
- **发布**：校验通过后生成 / 更新已发布版本，**并自动启用**。之后新提交用这个版本。**第一次发布成功，这张表才真正开始能填。**
- **启用流程**：开关。关掉等于「这张表暂时不走审批」：新数据按普通表单保存，但落库时直接记为已通过（§4.3），已发布版本保留，再点发布或打开开关不用重配。

从来没发布过：开关是关的，这张表按 §4.1 不能填。建错成流程表单又想当普通表用：删掉再建普通表单，不能转回去（§4.2）。

### 5.6 发布前要拦住的

画布：

- 没有开始，或开始不止一个
- 开始没有出线，或出线多于一条
- 没有任何审批节点
- 没有任何结束
- 某个审批没有名称或没有出线
- 某个分支出线少于 2 条，或没有恰好一条「其他情况」，或非默认线没配条件
- 存在从开始走不到的节点（提示节点名称）
- 存在走下去到不了任何结束的节点
- 存在环
- 结束上还连了出线

审批人：

- 某个审批没有审批人
- 审批人规则指向的角色已停用、人员已停用或已删
- 审批人规则选「表单内人员字段」，但字段已从画布删掉

表单字段以后又改了（增删改标题）：已发布流程仍可用。新增字段在老节点权限里视为「只读」。被删掉的字段 key 在权限表里保留无害，运行时找不到就忽略。人员字段被删导致某节点审批人解析不到人：待办派不出去，实例进「异常」（见 §16.5）。

## 6. 节点与连线（本期做哪些）

| 画布上是什么 | 本期 |
|---|---|

## 7. 审批人怎么定

审批人最终都要变成**具体用户 id 列表**，再给每人生成一条待办。

### 7.1 本期可选的三种来源（可组合）

属性里用和人员选择类似的配置，三种可以同时勾，结果取**并集去重**：

1. **指定人员**：从组织里勾人（复用登录可用的选人弹框 `front/src/components/form-fill/FormMemberSelect.vue`，不要走管理后台 `/admin/*`）。
2. **指定角色**：选一个或多个启用中的角色。运行时取「拥有这些角色、**角色本身仍启用**、账号启用」的人，默认再与发起人所在部门取交集（见下面的部门限定）。**这里要新建一个「选角色」的选择器**：现有登录端选人弹框的「角色」模式只是按角色筛人、不能选角色本身，唯一的角色下拉在 `/admin` 侧（管理后台），不要复用。
3. **表单内的人员字段**：下拉当前表单里的人员单选 `member` 或人员多选 `member-multiple`（含标签页里的，不含子表列）。提交时读这条数据里已选的人。字段为空则派发失败（§16.5）。

「发起人自己」不单独做一项：若需要，把发起人加进指定人员，或在表单里用人员字段填自己。

**「指定角色」默认限定与发起人同部门（已拍板）。** 角色是平台级的，按角色取人时没有部门维度（`server/src/org/org.service.ts` 按 roleId 过滤用户，不带部门条件）。若不加限制，「部门经理」这个角色下**所有部门**的经理都会收到**每个人**的请假待办——A 部门员工的请假派给了 B 部门经理，这是用户第一天就能撞上的错派。§7.2 说的「不做部门主管」不等于这个问题自动消失。

所以选了「指定角色」之后，下面出现一个勾选：**限定与发起人同部门**，**默认勾上**。

- 勾着：运行时取「拥有这些角色 ∩ 与发起人同一个部门 ∩ 账号启用」的人。一人一部门，数据现成（`user_department` 对 `userId` 有唯一索引），不需要给组织补「部门负责人」。
- 取消勾选：按角色取全公司的人。人事备案、财务审核这类本来就该全公司收单的节点用它。取消勾选时界面上提示一句「该角色下所有部门的人都会收到待办」，别让人无意间把请假派给别的部门。
- 存库字段 `sameDeptAsInitiator`（布尔，缺省当真）。

这个勾选只作用于**指定角色**：指定人员就是勾中的那些人，表单内人员字段就是那条数据里填的人，都不再按部门过滤。

### 7.2 本期不能选的（组织里还没有）

管理后台组织规格写明：一个人只属于一个部门，**没有部门负责人、没有汇报关系**。因此本期**不做**：

- 部门主管 / 上级
- 发起人部门的负责人
- 连续多级上报

以后组织里真补了「部门负责人」，再在审批人来源里加一项，不要先做假数据。

### 7.3 派发时的人名单

- 停用、已删除的用户：不进入待办。
- **指定角色运行时**：只取 `role.status = active` 且账号启用的人。角色后来停用了，不能再靠发布时查过一次就继续派。
- 三种来源合并后 **0 个人**：不能生成空待办。提交或流转到该节点时失败，提示「节点「xxx」没有可用的审批人」，实例保持上一状态（刚提交则记录已写入但实例进入「异常」见 §16.5）。
- **部门限定之后交集为空也算 0 个人**：例如发起人所在部门没有任何「部门经理」。提示要写清是部门限定导致的（「节点「部门审批」在发起人所在部门没有可用的审批人」），否则配置的人会以为是角色没配好，去查半天。出路仍是 §16.5 的重试或撤回改配置。
- **发起人没有部门记录**（组织里允许人员不挂部门时）：部门限定退化为不限定，按角色取全公司的人，并在流程进度里写一条「发起人没有所属部门，本节点按角色全公司派发」。不要因为查不到部门就直接派发失败——那会让一张正常的请假单卡在异常。
- **派发之后**审批人才被停用：待办已经生成，但那个人登录不了（账号停用后平台层每个请求直接拦掉，见权限规格 §12），这条单会卡住没人能批。本期没有转办，出路是 §16.5 的**重试**（重新解析审批人）。发起人、其他人在抽屉的进度里要看到「审批人已停用」，不要只显示一个再也不会动的待办。
- 名单里包含发起人：允许自己审自己，不做自动跳过。
- 同一人因角色+指定人员出现两次：只生成一条待办。

## 8. 发起人：草稿、提交、撤回

工作台打开流程表单时，「添加数据」这块还在，底部按钮改成：

- **保存草稿**
- **提交**
- 取消（和现在一样，不写库）

不再单独显示普通的「保存」当正式入库。

### 8.1 保存草稿

- 走现有必填校验：**草稿也要过必填**，和现在点保存一样。不做「草稿允许空着」——否则数据管理里会多出大量半截数据，和现有填报习惯不一致。
- 写入 Mongo 填报集合 `frm_{formId}`，和普通保存同一套 `data`、创建人、流水号（流水号仍是第一次落库时生成，之后不再变）。**创建人是当前填报的登录用户，不是应用所有者**（权限规格 §9；现有实现误写成 `ownerId`，开放使用范围时必须改掉）。
- 流程状态记为 **草稿**。没有待办，审批人看不见。
- 发起人可在首页「我发起的」打开抽屉继续改，再存草稿或提交。能进该表数据管理时，也可以从列表打开同一条。两条路鉴权不同，**保存必须是同一套**（§17）：类型转换、必填、子表、唯一、流水号、创建人/更新人。首页那条不要自己写 Mongo。
- 草稿可以删除，但必须发布页「删除」开着，而且只在**数据管理**里删。首页「我发起的」**没有删除入口**。发起人失去使用权之后进不了数据管理，**不能在首页删草稿**（权限规格 §8.1）。

### 8.2 提交

- 同样先过必填和子表等现有校验。
- **服务端也要校验**：现在后端保存填报时只校验子表列的必填、唯一字段和流水号（`server/src/application/form-record/form-record.service.ts`），主表字段的「必填」只在前端跑。提交是进入审批的入口，绕过去就是一条审批人看不全的半截单据。所以不管人是在工作台点「提交」，还是在首页「我发起的」点「再次提交」，后端都必须把主表必填一起校验，缺什么就返回哪个字段的提示（和前端同一套文案），不要只靠前端拦。工作台走 `intent = submit`；首页走流程实例那条提交接口，**里面仍调用同一套保存**，不要在流程服务里直接改填报。
- 若还没有记录：先入库再开流程。若已是草稿：更新字段再开流程。
- 读取**当前已发布**的流程版本，创建流程实例。从开始沿连线走：碰到分支就按这条数据算条件，直到落到第一个**审批**节点，给这些人派待办。若从开始一路只碰到分支就到了结束（没经过任何审批）：直接已通过——发布时应尽量避免这种图，但引擎仍按连线执行并提示「未经过审批即结束」。
- 状态变为 **审批中**（或上一句那种直接已通过）。
- 成功后提示「已提交，等待「部门审批」」（名称取实际落到的那个审批节点），工作台可以清空表单继续填下一张（和现在保存成功后清空一致）。

流程表单还没有已发布流程，却点了保存草稿 / 提交（或直接调接口）：服务端拦住，提示「这张表单还没有配置流程，发布流程之后才能使用」，**一条数据都不写**。普通表单没有提交按钮；若请求带了 `intent`，忽略 intent，按普通保存。

### 8.3 撤回

- 只有**发起人**能撤回。
- 只有状态是审批中，并且**还没有任何审批人点过「通过」**时可以撤回（第一个节点有人驳回过也不允许撤回，应走改完再提交）。
- 撤回要用**带条件的更新**做：一条语句里同时要求 `status = running` 且 `has_approved = false`，改不动就当作撤回失败并提示「审批人已开始处理，不能撤回」。不能先查一遍再改——发起人点撤回的同时审批人点通过，两边都以为条件成立。
- 失去该应用使用权的发起人（例如从使用范围里被移除）仍然可以在首页「我发起的」抽屉里撤回这条在途单据（权限规格 §8.1），只是不能再用应用里的入口。
- 撤回后：未处理待办全部取消（`status = cancelled`、`action` 留空，界面上显示「未处理（已取消）」，原因写「发起人撤回」）；状态变回 **草稿**；审批记录里留一条「发起人撤回」。发起人可改后再提交（新开一轮待办，仍是同一条数据、**同一个实例继续**，历史留着）。
- 已经处理完的待办（通过 / 驳回）不受影响，保留原样，别把它们改成取消。

审批中不能删除这条数据，只能撤回成草稿再删。

## 9. 审批人：通过、驳回

审批人从**项目首页「我的待办」**点一张卡片，打开的是**右侧抽屉**。可以复用现在的数据详情抽屉（`FormRecordDetailDrawer`）的排版，但**必须先把读和写抽成传入的数据源**：打开、选记录、联动、传文件、通过/驳回都走 `/api/workflow/...`，不能再 `import` 应用里的 `updateFormRecordApi`、字典、`records/query`。不抽数据源就复用，没有使用权的审批人会打不开，或整张表被顺手放开。**不要**让审批人先进入请假单所在的应用再批；能不能进那个应用，和能不能处理这条待办无关。

抽屉里多出的东西：

- 顶部：只读的小流程图（按提交时的画布缩略，当前审批节点高亮，已经走过的节点/连线用另一种颜色）。不要做成只能表示一条直线的步骤条，否则分支看不出来。
- 表单区：按**当前节点字段权限**显示；可编辑的字段能改，改完随「通过」一起保存。
- 底部左侧：审批意见输入框（按节点配置是否必填）。
- 底部右侧：**通过**、**驳回**、关闭。没有「编辑 / 保存」那套普通详情按钮。

同一条待办只能处理一次。两个人同时打开**同一条**待办：先提交的生效，后提交的提示「这条待办已处理」。**或签**下两人各有一条待办、同时点通过：先提交的那条让节点通过并取消另一条。**会签**下两人各有一条待办、同时点通过：两条都可以成功，都记已办；最后一人提交通过后节点才往下走。

### 9.1 通过

- 校验可编辑字段的必填（隐藏字段不校验；只读字段用库里已有值）。
- 意见按节点配置。
- 把可编辑字段的改动写回这条 Mongo 数据（只更新这些 key，别的字段不动）。联动带出的值也一样：**只写本节点标成可编辑的目标字段**；目标字段在本节点是只读或隐藏的，库里的值不动。
- 写回要复用现有的保存校验，**不要另开一条绕过校验的通道**：
  - **唯一字段**：审批人把可编辑的唯一字段改成别人的值，要拦下来并提示重复；校验时**排除本条自己**（`assertUniqueFields` 现在就是这么做的），否则没改也会报「已存在」。
  - **流水号** `serialNumber`：第一次落库时生成，之后永不再算。审批写回绝不能重新生成，否则同一条请假单在审批前后编号不一样，别人对不上账。
  - 子表列：本期审批里子表只读，不参与写回，也就不涉及子表校验。
- 按节点 **多人审批方式**（§5.3）分支：
  - **或签**：本节点其余未处理待办取消；沿**本节点唯一的那条出线**继续走（见下）。
  - **会签**：把当前这条待办标为完成，上面的写回**照常做**。若同节点还有 `pending` 的待办，**不**取消其余待办、**不**往下走，界面提示「已提交，等待其他审批人处理」。若这是本节点最后一条待办被通过，再沿出线继续走。
- 沿**本节点唯一的那条出线**继续走：中间若是分支，按**当前库里的数据**（含本次通过刚写回的可编辑字段）选线；落到下一个审批则派待办；落到结束则状态 **已通过**。

### 9.2 驳回

- 意见必填。
- 本节点其余未处理待办取消（**或签、会签相同**：任一人驳回即整节点驳回）。
- 状态变为 **已驳回**。
- 不自动改业务字段（审批人在驳回前改的可编辑字段：若已点驳回，**不写入**那些改动，避免「驳回却改了请假日期」。驳回只写意见和历史）。
- 发起人在首页「我发起的」打开这条，表单可改，底部是「保存草稿」和「再次提交」。再次提交后状态回到审批中，**从开始重新沿连线走**（用改过的新数据重新判断分支）。历史上已经点过的通过/驳回还在，小流程图从开始重新高亮即将到达的节点。

本期不提供「驳回到上一步」「驳回后结束不能再交」。

### 9.3 本期没有的操作

转办、加签、退回指定节点、审批中沟通@人、批量通过。需要改人时：管理员改节点配置只影响新提交；当前待办仍是已派发的那些人。

## 10. 我的待办、我发起的、我处理的

三处入口出现在**两个地方**，列表含义、卡片、抽屉、通过/驳回完全同一套，只是查询范围不同。

| 在哪 | 谁看得见 | 查出哪些单 |
|---|---|---|
| **项目首页**（和「我的应用」并列） | 每个登录的人 | **所有应用**里属于自己的 |
| **应用内左侧**（应用名下面、搜索/新建上面） | 已经能进这个应用的人 | **只限当前应用**的表单，别的应用的单不要出现 |

没有应用权限的人（例如只被派了人事请假的部门经理）**只能走首页**，不必、也不能进那个应用。有应用权限的人两条路都可以：首页批跨应用的，进应用只看本应用的。

表单工作台点进某张表后，仍然只有「添加数据 / 数据管理」（发布页对调只影响这两项）。**不要**把这三个入口做成某张表上的页签。

### 10.1 首页怎么进

顶栏在产品名右侧四个入口，当前页高亮：

**我的应用** · **我的待办** · **我发起的** · **我处理的**

「我的待办」可显示未处理条数（全应用合计）。

### 10.2 应用里怎么进

左侧从上到下固定是：

1. **应用名**（现有返回 + 名称，和现在顶栏一样）
2. **我的待办** · **我发起的** · **我处理的**（三行，不属于树节点、不能拖进分组）
3. **搜索 / 新建**
4. **分组和表单树**
5. **应用后台**

点其中一行待办入口，右侧主区换成对应的卡片列表（不再显示某张表的添加数据/数据管理）。「我的待办」可显示**本应用**未处理条数。本应用一张流程单都没有时，三行仍在，点进去是空状态。

### 10.3 三个入口分别列什么（两处相同）

| 入口 | 列出什么 | 点卡片后抽屉里做什么 |
|---|---|---|
| 我的待办 | 派给我、还没处理的任务 | 审批：通过 / 驳回（§9） |
| 我发起的 | 我作为发起人的流程数据（草稿、审批中、已通过、已驳回、**异常**） | 草稿/已驳回可改、【保存草稿】、【再次提交】；审批中可【撤回】（满足 §8.3）；**异常必须列出**，点开可以【重试】（也可以【再次提交】，见 §16.5）；**已通过一律只读**。没使用权的人不能改已通过。有使用权的人要改已通过，只能进该表【数据管理】，改完重新走审批（§11） |
| 我处理的 | 我点过通过或驳回的任务（取消的不算） | 只读再看当时的数据、意见和小流程图 |

都**用卡片 + 底部分页**，不要用表格。每页条数与项目其它列表相同（10 / 20 / 50 / 100）。空状态：「还没有待办 / 还没有发起过 / 还没有处理过」。应用内空状态可以写成「本应用还没有…」，避免人以为全站都没有。

### 10.4 卡片上写什么

跨表不能按某张表的列当表头，三处卡片用同一套缩略：

- 表单名称；**首页**再加应用名称（如「人事 / 请假单」）。应用内已经在这个应用里，卡片上**不必再写应用名**，只写表单名。
- 当前节点或流程状态（待办强调节点名，如「部门审批」；我发起的强调状态，如「审批中」；我处理的强调自己当时的动作，如「已通过」或「已驳回」）
- 发起人、时间（待办用到达时间，我发起的用提交或最后保存时间，我处理的用自己处理时间）
- 一两句摘要：该表若有适合当标题的字段（如事由、流水号）取前几个非空值；没有就只显示记录编号

卡片不要做成一行很多列的伪表格。点整张卡片打开右侧抽屉。

### 10.5 抽屉鉴权：按任务，不按「在哪个页面点的」

打开抽屉、读这一条、通过/驳回/撤回/再次提交，只看：

- 我的待办：当前用户是这条 **pending** 任务的处理人
- 我发起的：当前用户是这条实例的发起人
- 我处理的：当前用户曾经是这条任务的处理人，且任务已是通过或驳回

**不要**先校验「是不是应用创建人 / 应用成员」。首页进抽屉如此；应用里进抽屉也如此（人已经能进应用，但打开这一条仍然靠任务/发起人，不要改走数据管理那套 owner 接口）。

抽屉里用到的表结构、字典、人员姓名，按这一条单据放行，不能顺着去翻该表其它行。

通过 / 驳回 **只**从「我的待办」抽屉提交（首页或应用内同一抽屉）。数据管理里点开审批中的行：能看进度和历史，底部不出现通过 / 驳回。

### 10.6 查询必须带范围（服务端过滤）

同一个查询接口。首页不传应用；应用内**必须带当前应用 id**，服务端只返回该应用下表单的任务/实例。**不要**先查出全站再在浏览器里藏掉——翻页条数会错，也会把别的应用数据带到前端。

进了 A 应用的「我的待办」，B 应用的请假单即使也派给了当前用户，这里不能出现。那张单只在首页，以及 B 应用里。

### 10.7 组件怎么拆（首页和应用内共用）

两处交互必须一样，实现时拆成可复用块，不要复制两套页面：

1. **卡片列表**：负责请求（是否带应用 id）、分页、空状态、点卡片。
2. **一张卡片**：缩略信息；用一个开关决定要不要显示应用名。
3. **处理抽屉**：小流程图 + 表单区 + 底部按钮（【我的待办】：【通过】/【驳回】；【我发起的】：【保存草稿】/【再次提交】/【撤回】，异常时是【重试】；【我处理的】：只读）。

首页三个路由、应用内点侧栏三行，都只是「套一层」：告诉列表当前是待办 / 发起 / 处理，以及有没有应用 id。不要各写一套抽屉和卡片。

## 11. 数据管理里看到什么

数据管理列表比普通表单多一列 **流程状态**（草稿 / 审批中 / 已通过 / 已驳回 / 异常）。这一列只对流程表单出现，列设置里可关掉，默认开。流程表单上**不存在没有流程状态的记录**（§4.2 转换时已回填、§4.3 停用期间保存的直接记为已通过），所以这一列不会出现空值或「—」。

| 操作 | 流程表单怎么处理 |
|---|---|
| 【新增】 | 仍走【添加数据】那套（【保存草稿】/【提交】），【数据管理】里点【新增】同样进带【提交】的抽屉。**还没有已发布流程时不能【新增】**，提示「这张表单还没有配置流程」（§4.1）。关掉启用流程期间，抽屉底部回到【保存】，保存即记为已通过（§4.3） |
| 点行看详情 | 能看。审批中的详情只读，底部可看到进度和历史意见；**不**在这里通过 / 驳回（审批只从「我的待办」抽屉进，首页或应用内均可） |
| 编辑 | **草稿、已驳回、已通过：只有原发起人能改，别人只能看**（所有者、配置成员也不行）。草稿 / 已驳回：发起人可在数据管理或「我发起的」改。审批中：不能当普通编辑打开（没有铅笔、工具栏编辑对勾选的审批中数据提示「审批中的数据请到「我发起的」撤回或等待审批」）。**已通过：发起人也只能在数据管理里改**（「我发起的」只读），别人点开只能看。发布页「编辑」关着则发起人也不能改；开着则打开编辑抽屉，改完点提交后**重新走审批**——用**当前已发布**的流程版本，状态变回审批中，从开始再走一遍，别的表选记录弹窗暂时挑不到这条。发布页补一句说明：「改已通过的数据会重新进入审批，通过之前不能再被别的表选到。」关掉「启用流程」期间仍按 §4.3：保存即已通过，不建实例、不重审。没有实例的已通过（转换回填、停用期间保存）没有发起人，本期数据管理里只能看，不能拿去重审 |
| 删除 | **草稿、已驳回：只有原发起人能删**，还要发布页「删除」开着，只在数据管理里删；别人看不到删除。首页「我发起的」没有删除按钮。审批中不可删。已通过：跟发布页删除开关、走数据管理（谁能删以后做数据权限，本期先跟发布开关、能进数据管理的人） |
| 单元格内联编辑 | **整表关闭**。流程表单不提供列表里改格子，避免绕过节点权限 |
| 导入 / 下载模版 | **关闭**。导入会绕过审批。发布页这两项对流程表单强制关且不可再开 |
| 导出 | 仍按发布页（现在导出本身未做，保持不变） |

**已通过后在数据管理里改（已拍板，权限规格 §8.1）**

**没使用权**：已通过只能在「我发起的」里看，不能改。  
**有使用权、且我是原发起人**：首页「我发起的」里已通过的卡片同样只能看，没有「提交」。要改：进应用 → 打开这张表的数据管理 → 点这行编辑（发布页「编辑」得开着）。抽屉底部是「提交」，**没有**「只保存、不走审批」——点提交才写回并开新一轮，重新走审批。关掉抽屉不提交，库里仍是原来的已通过。  
**有使用权、但我不是发起人**：数据管理里这行只能看，没有编辑。A 交过的假，B 改不了。

提交之后：

- 这条还是同一条数据。已经有流程实例的，**同一条实例**开新一轮（`round` +1），从开始重新沿连线走，用**此刻已发布**的流程版本（§13、§16.3），不是当初那一版。发起人仍是当初提交的那个人，不改成别人。
- 转换时回填、停用期间保存的那种「已通过但没有实例」：没有发起人，本期不能从数据管理点编辑去重审。
- 状态变回审批中。别的表用关联数据 / 选择数据来挑，暂时看不到它（只出已通过）。已经关联上的格子仍显示原来的标题，不要因为重审把别人表上的值抹掉。
- 原发起人在「我发起的」里会看到它又变成审批中，可以按在途单据撤回或再交。

谁能在数据管理里改草稿 / 已驳回 / 已通过：**只有原发起人**，且发布页「编辑」开着。别人只能看。没使用权的发起人进不了数据管理，已通过只能看；草稿 / 已驳回仍可在首页「我发起的」改。

内联编辑现在是「每个格子自己判断能不能改」：`front/src/components/form-workspace/FormRecordCell.vue:207-208` 只看字段本身的 `isInlineEditable`，**没有任何整表或整行的开关**。所以「流程表单整表关闭」是要新加一层判断（这张表是流程表单 → 所有格子都不可内联编辑），不是去关一个已有的开关；实现时别指望现有配置能表达它。

上表的限制**前后端都要做**：前端不出铅笔、不出按钮只是体验，服务端的更新 / 删除接口必须按流程状态再判一次（审批中的记录拒绝普通更新和删除；已通过的记录拒绝「不带提交意图的普通更新」，必须走 §16.3 重新审批），否则用接口直接调就能绕过审批改数据。判定所需的流程状态从 Mongo 上的 `workflowStatus` 读（§15.2），必要时回查 MySQL 实例。

筛选：便捷筛选暂不包含流程状态（现有便捷筛选类型名单不变）。列表上方加一个流程状态下拉（全部 / 草稿 / 审批中 / 已通过 / 已驳回 / 异常），只对流程表单出现。

**没有实例的已通过记录**（转换时回填的、停用期间保存的）点开详情：表单数据照常显示，流程进度区写一句「转为流程表单之前保存，没有审批记录」或「流程停用期间保存，没有审批记录」，**不要**画一个空的小流程图，也不要显示「暂无进度」让人以为单据丢了。这两类记录在「我发起的」里也不会出现（没有实例），只在数据管理里能看到——它们本来就不是谁发起的审批。

## 12. 字段谁能改、谁只能看

分两套，不要混：

**发起填写（添加数据、草稿、已驳回再交）**

- 仍用字段自己的：必填、禁用、是否可修改、流水号只读等。
- 不看审批节点上的权限表。

**某个审批节点打开抽屉时**

- 可编辑：审批人能改，通过时写回。
- 只读：能看见，改不了。
- 隐藏：抽屉里不渲染（标签页里某字段隐藏则该格不出现；整个页签的字段都隐藏时，页签仍在，里面为空——不做自动藏页签，以免和现有标签页行为纠缠）。
- 子表单 `subform`：本期整表只读，不能在审批里增删改行。节点权限里子表只出现「只读 / 隐藏」，没有「可编辑」。这与子表规格「流程节点上的子表权限另立项」一致。
- 关联子表单 `relate-subform`：本来就是只读表格，权限里不出现（和分割线一样不当填报项）。
- 关联数据 `relate`、选择数据 `data`：可以标可编辑，审批人按现有控件重选。

登录人姓名、登录人部门、流水号：权限里可只读或隐藏，不能标可编辑。

## 13. 流程改了、老单据怎么办

流程定义带版本号，从 1 递增。

- **保存草稿**：改未发布的设计稿，不影响任何人。
- **发布**：版本 +1，成为新的已发布版本。之后的新提交、草稿首次提交，都用新版本。
- **已经在审批中的实例**：钉死在**提交当时**的版本。设计器里删掉「人事备案」或改审批人，不影响这张正在走的请假单。
- **已驳回后再次提交**：仍用**该实例钉死的旧版本**，不悄悄换成新流程，避免同一条单据前后节点对不上。发起人若要走新流程，只能删掉这条（若允许）再新建。
- **已通过后又在数据管理里提交**：开新一轮时改用**当前已发布**的版本（把实例上的版本和流程图快照换成现在这份）。这和已驳回再交不同：已通过已经走完，再改是新一轮业务，应当跟此刻的流程走。

界面上流程设计页显示「当前已发布版本 v3。审批中的 2 条仍按提交时的版本走。」

## 14. 和现有功能怎么相处

| 能力 | 流程表单下的约定 |
|---|---|
| 流水号 `serialNumber` | 第一次保存草稿或直接提交时生成，之后再提交、审批改字段都不变 |
| 数据联动 | 发起填写、审批人改可编辑的条件字段时，照常带出。带出的值**只写本节点可编辑的目标字段**；目标是只读或隐藏的，库里不动。列表内联编辑本来就不跑联动，流程表单也没有内联编辑 |
| 选择数据 `data` / 关联数据 `relate` | 当**本表是源表**时：别的表弹窗选记录，只列出流程状态为已通过的。判定「本表是不是流程表」看 `app_form` 上的类型列（§15.1），**不是**看有没有已发布流程——否则停用期间的数据会漏筛。普通表不受影响 |
| 关联子表单 `relate-subform` | 主表详情里列子表数据时，子表若是流程表单，只列出已通过的行 |
| 下拉「其他表数据」 | 选项取的是字段值不是记录资格，**不过滤**流程状态（和现在「存的是值不是关系」一致） |
| 表单类型与转换 | 类型在建表时选（§4.1）。之后只能普通 → 流程（回填已有记录为已通过）。流程表单不能转回普通。转换属于设计类操作，只有所有者和配置名单上的人能做（权限规格 §6.3） |
| 停用期间的保存 | 关掉「启用流程」后按普通表单保存，落库即记为已通过、不建实例（§4.3）。这些数据在选记录弹窗里照样能挑到，在「我发起的」里不出现 |
| 人员 / 部门 | 审批人指定人员和表单内人员字段，用同一套组织接口。指定角色默认再与发起人所在部门取交集（§7.1） |
| 标签页 `tabs` | 流程可绑在整张表上，不能给某个页签单独绑流程 |
| 子表单 `subform` | 发起时按现有规则填；审批里只读（§12） |
| 表单发布「新增/编辑/删除」 | 仍有效，但叠加 §11 的流程状态限制；导入模版对流程表单强制关 |
| 谁能发起填写 | **发起填写**仍在应用工作台「添加数据」，要有该应用的**使用权**（所有者、配置名单、使用范围命中，任一即可；权限规格 §6.3、§7.3）。应用使用范围（TODO P7 / 权限规格第 2 期）没做之前：能进工作台的人就能发起，也能看见应用内这三行 |
| 谁能看到三个待办入口 | **我的待办 / 我发起的 / 我处理的**：首页跨应用，每个登录的人都能进，**不看使用权**；应用内左侧在应用名下面、搜索/新建上面再有一份，只查本应用，人必须已经能进这个应用。审批人**不必**有使用权——没有就只走首页，批完不能顺着翻该表数据管理；同时有使用权的人本来就能看该表全部行，那是使用权给的，不是流程的漏洞（权限规格 §8 第 5 条）。**失去使用权的发起人**只能在首页「我发起的」继续处理在途单据（草稿 / 审批中 / 已驳回 / 异常），进不了应用、打不开数据管理；已通过只读，要改必须还能进应用走数据管理，改完重新审批（权限规格 §8.1） |

实现硬条件（细节以权限规格为准，本文只列流程会碰到的）：

- 现有 `FormRecordService`、`getForm`、字典接口都按**应用所有者**鉴权（`requireOwnedApp`，`server/src/application/application.service.ts:376-382`）。流程上线时要拆成 `AppAccessService`：进应用看「能使用」（所有者、配置者、使用范围内的人），**读字典同样按能使用**（权限规格 §12）；设计 / 后台 / 改字典看「所有者或配置」，删应用和移交只看所有者，**首页待办不走这条**（权限规格 §12.1）。
- 读 / 写**单条**记录要增加按 **任务或发起人** 放行的入口，两个入口（首页、应用内）共用，**不要**先 `requireOwnedApp`。写仍只允许引擎和规则里允许的人。首页再存草稿 / 再交：鉴权按发起人，保存仍走 `FormRecordService` 同一套，不要流程服务自己写 Mongo（§17）。
- 待办抽屉的读和写**全部**走 `/api/workflow/...`（打开一次带齐结构 / 字典 / 本条数据；选记录、联动、传文件另走 `render/:instanceId`）。`/apps/:appId/...` 一条都不为待办开例外。详见权限规格 §8.2。
- 三个列表走流程任务 / 实例查询，可选 `appId` 过滤；不要复用数据管理的 `records/query`。

## 15. 库里怎么存

配置走 MySQL，填报仍走 Mongo，和现有混合存储一致。**不要**为流程再给每张表建一张业务表。

### 15.1 MySQL（流程自己的表）

**命名按项目现有习惯，别照抄下面的蛇形写法**：现有表都是**单数下划线表名**（`app_form`、`app_group`、`user_role`、`dictionary_item`），列是**驼峰属性名**（TypeORM 不配命名策略，列名就等于属性名，如 `applicationId`、`createdAt`），普通索引用 `IDX_表名_属性`，**唯一约束用 `uk_表名_属性`**（对照 `uk_user_department_userId`），没有 `BaseEntity`，时间列显式写 `@CreateDateColumn` / `@UpdateDateColumn`（对照 `server/src/application/app-form.entity.ts`）。所以下面表格里的 `app_id` 实现时应写成 `appId`、`form_id` 写成 `formId`，以此类推；表格用蛇形只是为了读起来清楚。

建议表名（三张）：`workflow_definition`、`workflow_instance`、`workflow_task`。

**表单类型存在现有的 `app_form` 表上**，新增一列（如 `formKind`：`normal` / `workflow`），**不要**放在流程定义表里。原因是「还没配流程的流程表单」在流程定义表里根本还没有行，判定不出来，数据就会按普通表单落库（§4.1）。已有的表单全部按 `normal` 处理，行为不变。转换（§4.2）只改这一列，外加按需回填 Mongo 上的 `workflowStatus`。

**流程定义**（一张表单一份「当前设计稿 + 已发布版本」即可用两行策略，或一行里带 draft_json + published_json + version。推荐一张表）：

| 人怎么理解 | 存什么 |
|---|---|
| 属于哪个应用、哪张表 | `app_id`、`form_id`，`form_id` 唯一 |
| 有没有启用 | `enabled` |
| 设计中的流程图 | `draft_graph`（JSON：节点 + 连线 + 坐标） |
| 已发布的流程图 | `published_graph`（同上，可空表示从未发布） |
| 已发布版本号 | `published_version`，从未发布为 0 |
| 何时发布 | `published_at` |

`form_id` 要建**唯一约束**（一张表最多一份定义，避免并发保存出两行）；`app_id` 建普通索引，供「本应用有几张流程表」「应用内待办按 appId 过滤」这类查询用。删除表单时连带删掉这张表的定义行，不要留孤儿数据（现有 `deleteForm` 已经会 drop Mongo 集合，见 `server/src/application/application.service.ts:362-374`）。

**流程实例**（一条填报最多一条实例）：

| 人怎么理解 | 存什么 |
|---|---|
| 哪条数据 | `form_id` + `record_id`（Mongo 那条 id 字符串），`app_id` 也存一份，应用内待办按应用过滤时不必回连定义表 |
| 按哪个流程版本走 | `definition_version` + 当时的 `graph` 快照（整份 JSON 拷进来，版本被以后的发布覆盖也不丢） |
| 谁发起的 | `initiator_id` |
| 现在到哪 | `status`：`draft` / `running` / `approved` / `rejected` / `error`。撤回回到 `draft`，不另做「已撤回」 |
| 当前审批节点 | `current_node_key`，停在审批上等人为该审批的 key；草稿和结束时可空。分支不算「当前节点」 |
| 已经走过的节点 | `visited_node_keys`（数组，给小流程图上色） |
| 有没有人已经点过通过 | `has_approved`，给撤回判断用 |
| 第几轮审批 | `round`，从 1 开始。驳回后再次提交、撤回后重新提交、已通过后在数据管理里再提交都 +1。任务表带同一个 `round`，历史才分得清「上一轮的通过」和「这一轮的通过」 |
| 为什么异常 | `error_reason`（人话，如「节点「部门审批」没有可用的审批人」），只在 `status = error` 时有值 |
| 异常停在哪一步 | `retry_step`，配合 §15.3 的顺序约定用：重试时只补这一步之后的动作，不重跑已经成功的步骤 |
| 写回失败待补的内容 | `retry_patch`（审批人通过时填的字段值）。审批写回 Mongo 失败时先把要写的内容存这里，重试补写成功即清空 |
| 待补内容是谁填的 | `retry_actor_id`，与 `retry_patch` 同存同清 |
| 时间 | `started_at`（首次提交）、`ended_at` |

`form_id + record_id` 建**唯一约束**：一条填报最多一条实例，并发提交不会开出两条。`initiator_id`、`app_id + status` 建索引，分别供首页「我发起的」和应用内三个列表查。

草稿：可以「有 record、有 instance 且 status=draft」，提交时同一条 instance 改成 running。这样撤回、再提交都对着同一行。保存草稿时就创建 instance，避免 record 和流程对不上。

`retry_step` 不是给人看的，是给「重试流转」用的。没有它，重试只能整段重跑：Mongo 已经改过的字段会被再改一次，或者已经派出去的待办被派第二遍，同一个人收到两条一样的待办。

**待办任务**

| 人怎么理解 | 存什么 |
|---|---|
| 属于哪个实例、哪个节点 | `instance_id`、`node_key` |
| 第几轮 | `round`，与实例上的 `round` 一致。没有它，驳回再提交后历史里会出现两条同节点的「通过」，分不清哪条是这一轮的 |
| 给谁 | `assignee_id` |
| 状态 | `pending` / `done` / `cancelled` |
| 人点了什么 | `action`：`approve` / `reject`，未处理为空 |
| 意见 | `comment` |
| 为什么被取消 | `cancel_reason`（系统写：或签其他人已通过 / 或签其他人已驳回 / 会签节点已驳回 / 发起人撤回），只有 `cancelled` 有值 |
| 时间 | `created_at`、`finished_at` |

`instance_id + node_key + assignee_id + round` 建**唯一约束**：同一轮同一节点，一个人只可能有一条待办。§7.3 说的「角色 + 指定人员命中同一人只生成一条」靠派发前去重，再靠这条约束兜住并发。`assignee_id + status` 建索引，「我的待办」按人查未处理任务全靠它。

删除记录时的连带处理：**删一条草稿就删干净**——实例和它下面的任务（含撤回留下的已取消待办）一起删，不留孤儿。已通过 / 已驳回的记录被删掉时，实例和任务**保留**，只是记录没了——否则历史对不上账。三个待办入口里这类卡片仍列出，标「数据已删除」，只能看进度、不能改。点开不要报错。

**历史**（只追加，待办取消也写一条系统记录以免对账只靠任务表）

列表「进度 + 意见」从任务表就能拼：已完成的通过/驳回 + 取消原因（系统：或签其他人已通过 / 或签其他人已驳回 / 会签节点已驳回 / 发起人撤回）。若展示够用，可以不另建 history 表；**本期用任务表当历史**，少一张表。取消的任务 `action` 为空、`status=cancelled`，界面显示「未处理（已取消）」。

### 15.2 Mongo 填报文档

`frm_{formId}` 文档根上增加冗余，方便列表筛，**不以它为权威**：

| 键 | 含义 |
|---|---|
| `workflowStatus` | 与实例 `status` 同步：`draft` / `running` / `approved` / `rejected` / `error`。**流程表单上的每条记录都有这个键**。普通表单**不要写**这个键（流程表单不能转回普通，不会在普通表上留下旧键） |
| `workflowInstanceId` | MySQL 实例 id。走过审批的记录才有；转换回填和停用期间保存的记录**没有**（它们没有实例） |

写这两项只允许流程引擎和 §4.2 / §4.3 那两条明确路径在同一业务操作里更新。填报的 `data` 形状不变。

**流程表单上的 `workflowStatus` 有三个来源**，凑起来保证「没有缺键的记录」：

1. 走完审批（或正在走）：引擎按实例状态同步写。
2. 普通表单**转为流程表单**时的一次性回填：已有记录写 `approved`，不建实例（§4.2）。只写还没有这个键的记录，已有的不动；大表分批更新，别一条语句锁住整张集合。
3. **关掉启用流程期间**保存的数据：落库时直接写 `approved`，不建实例（§4.3）。

**给「选择数据 / 关联数据」弹窗筛「只已通过」时，先要知道这张源表是不是流程表**，两种情况规则不同，不要合成一条查询：

- 普通表：现有 query，**不加**任何流程条件，所有行都能被挑。
- 流程表：只取 `workflowStatus = approved`。

**不要**写成「`workflowStatus` 不存在也算通过」。把「默认放行」当成筛选规则，风险方向是错的：哪天有代码忘了写这个键，审批中的单子就会被别的表当正式记录挑走。上面三个来源已经把缺键这种情况消灭掉了，所以这条规则不需要任何特例。

判断「这张表是不是流程表」的依据是 **`app_form` 上的类型列**（§15.1），**不是**「有没有已发布的流程」，也**不是** Mongo 文档上有没有这个键。用「有没有已发布流程」判定会漏掉两种情况：从来没发布过流程的流程表单（它按 §4.1 根本填不进去、没有数据，这条筛选规则轮不到它，但判定依据仍要看类型列，否则以后发布了流程、或发布后又关掉启用，同一张表会在两套规则之间来回跳），以及关掉启用流程的流程表单（它没有「正在用的已发布流程」，但数据是带 `approved` 的，仍要按流程表的规则筛）。

管理员作废整单本期不做。撤回只回到草稿。

### 15.3 事务

一次「通过」要改：Mongo 字段、Mongo 状态、MySQL 任务、MySQL 实例。没有跨库事务。

顺序约定：

1. 先在 MySQL 把待办从 pending 改成 done（带条件更新，防并发）
2. 再写 Mongo 的 data 补丁和 `workflowStatus`
3. 再派下一节点待办或把实例标结束

若 2 失败：待办已是 done，实例仍 running，进入 **异常**（§16.5），提供「重试流转」而不是让用户再点一次通过。若 1 失败：整单当没点过，用户重试。

**顺序里要顺手把「走到第几步」写进实例的 `retry_step`**（§15.1）。只记「异常了」不够：异常可能停在三步里的任意一步，重试时必须知道前面哪些已经生效。

| 停在哪 | 已经生效的 | 重试要补的 |
|---|---|---|
| 第 1 步失败 | 什么都没改 | 不用进异常，用户重新点一次通过即可（条件更新会告诉他这条待办已被处理） |
| 第 2 步失败 | 待办已 `done` | 只写 Mongo 补丁和 `workflowStatus`，然后接着做第 3 步。**不要**再把待办改一遍，也不要让用户重新点通过——他的意见已经记下了 |
| 第 3 步失败 | 待办已 `done`、Mongo 已写 | 只派下一节点待办或把实例标结束 |
| 第 3 步里派单失败（`retry_step = 'dispatch'`） | 待办已 `done`、Mongo 已写，但下一节点的待办没派出去 | 重新解析当前节点并派单；解析不出审批人仍进异常，不重写 Mongo、不动已完成的待办 |

重试要幂等：同一个 `retry_step` 重跑两次，结果必须一样。所以派待办靠 §15.1 那条唯一约束兜底，Mongo 写的是「把这些 key 设成这些值」而不是「往上加」，实例状态更新都带条件（`status = error`）。界面上「重试流转」点一次就置灰，避免连点。

谁能点重试：发起人自己（首页「我发起的」），或该应用的所有者 / 配置名单上的人（能进应用，在数据管理打开这条异常单据后点；权限规格 §12）。审批人不能点——他没权限改这条数据的流转，也不该在异常时替系统做决定。系统管理员也不能点（打不开应用）。

## 16. 引擎规则（按人点的顺序）

### 16.0 沿连线走到下一个停留点

提交、通过、再次提交之后，都要「从某个点往下走，直到必须等人或结束」：

1. 从指定节点的出线出发（提交、再次提交从开始的出线出发；通过从刚通过的那个审批的出线出发）。
2. 下一格是 **分支**：按出线 `sort` 依次算 `when`，命中第一条；都不中走 `isDefault` 那条。条件里的值读**此刻** Mongo 里的 `data`（通过时含刚写回的补丁）。
3. 下一格是 **审批**：停下来派待办，写入 `current_node_key`，并把该节点推进 `visited_node_keys`。
4. 下一格是 **结束**：状态改为已通过，清空当前节点。
5. 下一格缺失、条件算不出来又没有「其他情况」、或走到环（快照若被改坏）：进异常，原因写清。

分支本身不进待办。经过的分支 key 也写入 `visited_node_keys`，小流程图才能把走了哪条岔画出来。

### 16.1 状态

```text
保存草稿 → draft
提交 / 再次提交 → running
沿连线走到结束 → approved
任一节点驳回 → rejected
撤回 → draft（has_approved 仍为假）
派发不到人 / 写库中断 → error（界面显示「异常」，发起人或能进应用的所有者 / 配置成员可点重试；审批人和系统管理员不能点）
```

不允许的跳转（直接拒绝）：`approved` → 再提交；`running` → 普通编辑保存；`draft` → 审批人通过。

### 16.2 多人审批方式（或签 / 会签）

审批节点快照里带 `signMode`（`any` | `all`），缺省当 `any`（或签）。同一 `node_key` 下可能有多条 `pending` 任务（审批人并集去重后每人一条）。

**或签（`signMode = any`）**

- 任一条待办变成 `done` + `approve` 后，其余同节点 `pending` 改为 `cancelled`，取消原因记「或签其他人已通过」。
- 任一条变成 `done` + `reject` 后，其余 `pending` 改为 `cancelled`，取消原因记「或签其他人已驳回」。
- 通过时写 Mongo、沿出线往下走，与 §9.1 一致。

**会签（`signMode = all`）**

- 任一条变成 `done` + `reject` 后，其余同节点 `pending` 改为 `cancelled`，取消原因记「会签节点已驳回」；实例 `rejected`，与 §9.2 一致。
- 任一条变成 `done` + `approve` 后：**立刻写回这个人改的可编辑字段**（§9.1 的校验同样跑一遍）。不要等到最后一个人通过再一起写——那样前面几个人改的东西会被丢掉，抽屉里明明改成功了，库里却没有。
- 写回之后：**若**同节点仍有 `pending`，只更新本条，实例 `current_node_key` 不变，不派下一节点，界面提示「已提交，等待其他审批人处理」。
- **若**本条通过后同节点已没有 `pending`（所有人都已通过），才沿出线往下走。
- 两个人改了同一个可编辑字段：后提交的覆盖先提交的（和单元格内联编辑的「后写赢」一致）。本期不做冲突提示，但节点权限里同一个字段别配给多人可编辑，配置时自己避免。
- 并发：两人同时通过且是不同 `assignee` 的两条待办，两条都应能 `done`；引擎用「本节点 `pending` 计数是否为 0」决定是否流转，必须用条件更新防重复推进（否则两条都以为自己是最后一条，流程往下走两遍、下一节点派出两份待办）。

**只有一名审批人**

- `signMode` 任意，行为与或签通过 / 驳回相同（没有「等其他人」）。

### 16.3 再次提交

`rejected` → 校验（含 §8.2 说的服务端主表必填）→ 更新 data → `running`，`round` +1，`has_approved` 置回假，按**实例快照里的图**从开始重新走 §16.0。旧任务都已是 done/cancelled，新任务带新的 `round` 和新 id。`visited_node_keys` 从本轮重新记（上一轮走过的仍能从旧任务看历史，小流程图「本轮路径」用新数组）。

用的仍然是**这条实例钉死的版本**（§13），不是最新发布的那份。

`error` 状态的实例也允许发起人重新提交（等价于撤回成草稿后再交），不必先手动点重试。

**已通过后从数据管理再提交**（§11）：只有原发起人能调。`approved` → 同样校验、更新 data、`running`、`round` +1、`has_approved` 置回假，把实例上的版本和流程图快照换成**当前已发布**的，再从开始重新走。没有实例的已通过记录（转换回填、停用期间保存）本期不能从这条路重审。一条填报仍然最多一条实例（`form_id + record_id` 唯一约束）。

### 16.4 并发

- 完成待办必须用「id + status=pending + assignee=当前用户」更新，影响行数 0 则提示已处理。不要先读再写无条件更新。
- 撤回必须用「实例 id + status=running + has_approved=false」更新，影响行数 0 则提示「审批人已开始处理，不能撤回」。
- 再次提交 / 提交草稿必须用「实例 id + status 属于 draft、rejected」更新；数据管理里对已通过再提交必须用「实例 id + status = approved」更新。都是为了防止同一条被点两次提交开出两轮待办。
- 会签最后一人通过的流转，靠「本节点 pending 计数为 0」+ 实例上的 `current_node_key` 仍是本节点做条件更新，防止两人同时成为「最后一个」而流转两遍。

### 16.5 异常（error）

出现时机：

- 提交或流转时审批人名单为空（三种来源都没解析出启用中的人）
- 快照里的图走不通：出线缺失、分支条件算不出来又没有「其他情况」、走到环
- 人员字段被表单设计删掉，节点解析不到人（§5.6）
- **派发出去的审批人后来全部停用**：待办还在，但没人登录得了。本期没有转办，只能靠重试重新解析审批人；界面上要写清「审批人已停用」，不要只显示一个永远不动的待办
- MySQL 已落点、Mongo 写入失败（§15.3）

界面：

- 发起人在首页「我发起的」看到状态「异常」和原因（「节点「部门审批」没有可用的审批人」/「写入数据失败，请重试」）
- 提供 **重试**：按 §15.3 的 `retry_step` 补未完成的动作——重新解析审批人并派待办，或重放未完成的 Mongo 写入。**幂等**，重复点不会派出两份待办
- 提供 **撤回成草稿**（与 §8.3 相同条件放宽：error 且无人成功通过时也可以撤）
- 谁能点重试：**发起人**（首页「我发起的」，没使用权也可以），或该应用的所有者 / 配置名单上的人（能进应用，在数据管理打开这条异常单据后点；权限规格 §12）。审批人不能点。系统管理员不能点。失去使用权的发起人仍可在首页重试（权限规格 §8.1）

不要静默停在审批中却没有任何待办。

## 17. 人在系统里会碰到的接口（先说事，再写路径）

鉴权：已登录。**设计流程**看「所有者或配置名单」（权限规格 §12.1，取代现在的 `requireOwnedApp`）。**在工作台添加数据、数据管理**看「所有者、配置名单或使用范围命中」。**首页三个入口**不带应用，走 `/api/workflow/...`，只按任务或发起人授权，**不校验应用权限**。

设计类接口仍挂在表单下，与现有 `/apps/:appId/forms/:formId/records` 并列。首页类接口挂在平台根上，因为人还没进任何应用——尤其是没有使用权的审批人，他根本没有 `/apps/:appId` 这条路可走。

| 人做的事 | 方法与路径（草案） |
|---|---|
| 打开流程设计，看到草稿和已发布版本 | `GET /api/apps/:appId/forms/:formId/workflow` |
| 保存流程草稿 | `PUT /api/apps/:appId/forms/:formId/workflow/draft` |
| 发布流程、开关启用 | `POST .../workflow/publish`、`PATCH .../workflow`（enabled） |
| 转换表单类型（只允许普通 → 流程） | `PATCH /api/apps/:appId/forms/:formId/kind`，body：`formKind`（只能是 `workflow`，与 §15.1 的列同名；不要叫 `kind`，下面 inbox 查询已经用 `kind` 表示待办 / 发起 / 处理）。设计类权限（所有者或配置名单）。只接受普通表单改成流程表单，并回填已有记录为已通过；**不要**只改一列就返回。已经是流程表单、或 body 想改回 `normal`：拒绝 |
| 保存草稿数据 | 仍用工作台 `POST .../records`，增加可选 `intent: 'draft' \| 'submit'`，普通表单忽略该字段 |
| 工作台提交 | 同上，`intent: 'submit'`；已有 id 则 `PATCH .../records/:id` 带 `intent` |
| 数据管理里改已通过并提交 | 同一条 `PATCH .../records/:id`，`intent: 'submit'`。必须是原发起人。服务端看到当前是已通过，走 §16.3「已通过后再提交」（换当前已发布版本），不要当成普通更新直接写完仍保持已通过 |
| 首页「我发起的」再存草稿 / 再次提交 / 撤回 | `POST /api/workflow/instances/:instanceId/draft`、`.../submit`、`.../cancel`。鉴权只认发起人，不校验能不能进应用。**保存必须走与上一行 records 同一套**（类型转换、必填、子表、唯一、流水号只生成一次、创建人/更新人写当前登录人），成功后再改实例、派待办。不要在这条接口里直接写 Mongo。撤回只改实例和待办，不改填报字段 |
| 我的待办 / 我发起的 / 我处理的 | `POST /api/workflow/inbox/query`（kind=`todo` \| `mine` \| `done`；可选 `appId`：有则只查该应用，无则全站），返回卡片所需缩略 + 分页 |
| 打开抽屉看一条 | `GET /api/workflow/inbox/:kind/:id`（待办/已处理用 taskId，我发起的用 instanceId）。一次带回表单结构、本条数据、**该应用字典项**、小流程图、人名、本条已有文件地址、底部可做什么。不要再去调 `/apps/:appId/...`（权限规格 §8.2） |
| 抽屉里选记录 / 联动 / 传文件 | `POST /api/workflow/render/:instanceId/source-records`、`.../linkage`、`POST/GET .../files`。仍按这条实例授权；只查该字段的源表或本条已有文件。**不要**复用 `records/query` 或应用内上传。发起人只在草稿 / 已驳回 / 异常时能写入和上传；审批中、已通过只读。审批人按节点字段权限；「我处理的」只读 |
| 通过 / 驳回 | `POST /api/workflow/tasks/:taskId/complete`，body：`action`、`comment`、可编辑字段的 `data` 补丁 |
| 重试异常 | `POST /api/workflow/instances/:instanceId/retry`（发起人，或能进应用的所有者 / 配置名单上的人。审批人和系统管理员不能调） |
| 数据管理列表带状态 | 现有 `records/query` 增加可选 `workflowStatus`；返回每条带 `workflowStatus` |
| 关联数据弹窗只选已通过 | 现有 query 增加服务端判断：源表是流程表单则强制 `workflowStatus=approved` |

**两扇门，一间库房（已拍板）**：工作台 / 数据管理走 `/apps/.../records` + `intent`（先判能使用）；首页「我发起的」走 `/api/workflow/instances/.../draft|submit`（先确认是发起人）。两扇门鉴权不同，写进填报的保存只留一套（现有 `FormRecordService` 里的类型转换、校验、流水号；实现时把「保存」和「必须是所有者」拆开，否则失权发起人调不到）。引擎只在保存成功后启动或推进。不要给失权发起人开放 `PATCH /apps/.../records`，也不要在流程服务里另写一套入库。

## 20. 分期（做完一期要能真正请假）

**第 1 期（本文必须一次做完才能叫流程表单）**

- 流程设计器：拖审批 / 分支 / 结束，从开始连线，分支线上配条件，保存坐标
- 发布校验（孤点、环、缺「其他情况」、缺审批人等）
- 三种审批人（含**指定角色的「限定与发起人同部门」勾选**，默认勾上）、**或签 / 会签**（节点属性可配）、启用开关、版本钉死
- 引擎按连线 + 分支条件走；草稿 / 提交 / 撤回 / 通过 / 驳回 / 再次提交（含会签「等所有人」）
- **表单类型**：建表时选普通 / 流程；流程表单没发布流程前不能填（前端拦 + 服务端拦，草稿也不写库）
- **类型转换**：只做普通 → 流程（回填已有记录为已通过，分批）；流程表单不能转回普通
- **停用期间**按普通保存并直接记为已通过，不建实例
- 首页 + 应用内左侧「我的待办 / 我发起的 / 我处理的」（同一套卡片和抽屉；首页跨应用，应用内只查本应用）
- 节点字段权限（主表，含子表只读或隐藏）
- 数据管理状态列与限制（审批中不可编辑 / 不可删、**内联编辑整表关闭**、导入模版强制关）；草稿 / 已驳回 / 已通过只有原发起人能改，已通过改完用当前已发布版本重新审批；关联 / 选择数据只挑已通过
- **服务端校验**：提交 / 再次提交时后端校验主表必填（现在只校验子表），审批写回复用唯一校验且不重算流水号；首页「我发起的」再存 / 再交与工作台走同一套保存（§17）
- 待办抽屉按权限规格 §8.2：读和写全部走 `/api/workflow/...`（打开带齐结构 / 字典 / 本条数据；选记录、联动、文件走窄接口），不要求能进应用
- 异常与重试（重试按 `retry_step` 幂等补做，不重复派待办）

**第 2 期（常用增强，另开规格）**

- 抄送、并行（同时走两条）
- 转办、驳回指定节点
- 首页待办再按应用 / 表单筛选
- 审批里按节点改子表

**第 3 期**

- 部门负责人、超时催办、站外通知
- 流程模板跨表复用、导入导出流程图

## 21. 验收（按【请假单】点）

1. **新建表单时选类型**：选【普通表单】建出来的表，顶栏只有三个页签、【添加数据】底部是【保存】，行为和现在完全一样。选【流程表单】建出来的表，顶栏多出【流程设计】。
2. **流程表单还没发布流程就去填**：打开【请假单】的【添加数据】，顶部有常驻提示；点【保存草稿】和【提交】都提示「这张表单还没有配置流程」，【数据管理】里查不到任何新记录（服务端也拦，直接调接口同样写不进去）。首页三个流程入口可以有，但【请假单】不会出现在里面。
3. **画布上拖出 §2 那张图（开始→分支→事假进部门审批、病假进人事备案→汇合人事备案→结束），配好审批人并点【发布】**：【添加数据】底部变成【保存草稿】、【提交】；【请假单】上**没有**待办页签。能进【人事】的人，左侧应用名下面能看到【我的待办】等三行（在搜索/新建之上）。没有连线或分支缺「其他情况」时点【发布】会被拦住。
4. **必填没填就【提交】**：仍提示请填写某字段，不进审批。
5. **【保存草稿】**：【数据管理】能看到一条「草稿」；首页【我的待办】没有；发起人在【我发起的】能看到这张卡片；别的表用关联数据来挑【请假单】，看不到这条。
6. **【提交】事假**：提示等待部门审批；**与发起人同一个部门**的部门经理每人在首页【我的待办】多一张卡片（即使他们打不开【人事】）；**别的部门的经理收不到**；张三还没有；发起人在【我发起的】能【撤回】。
7. **另提一条病假（人事备案是会签）**：不经部门审批，张三、李四首页【我的待办】都多一张卡片。
8. **事假被经理【通过】**：意见选填可空；经理这张卡片从【我的待办】消失、出现在【我处理的】；张三、李四【我的待办】都出现卡片；其他经理待办消失；小流程图高亮人事备案。
9. **会签：张三点【通过】**：事由若节点标了可编辑，能改；点【通过】后流程仍停在人事备案，李四的待办还在，状态不是已通过。李四点【通过】后才到结束，别的表关联数据这时才能挑到【请假单】。张三不必进【人事】。若张三也能进【人事】，应用内【我的待办】点同一张卡片，抽屉和按钮与首页相同。
10. **经理【驳回】事假**：必须写意见；发起人在【我发起的】改成病假再点【再次提交】；本轮不再出现经理待办，直接到张三、李四。
11. **或签：人事备案改成或签后再【提交】一张病假**：张三、李四都收到待办；张三点【通过】后李四的待办取消，整单已通过，不等李四。两人同时点【通过】：一人成功，另一人提示已处理。
12. **会签里任一人【驳回】**：张三点【驳回】后李四的待办取消，状态已驳回。
13. **【发布】前删掉所有审批节点，或分支只留一条线**：不能【发布】。
14. **审批中改画布并【发布】**：进行中的那张【请假单】仍按【提交】时的图走；新【提交】的按新图。
15. **审批中去【数据管理】点【编辑】、点单元格**：不能当普通数据改掉。
16. **角色里没人、或人员字段空着就【提交】**：不能变成「审批中但没人有待办」，应提示异常并可【重试】或【撤回】。
17. **「人事备案」节点取消勾选「限定与发起人同部门」**：该角色下所有部门的人都收到待办（或指定人员张三、李四照旧）。配置时取消勾选会有「所有部门的人都会收到待办」的提示。
18. **发起人所在部门没有「部门经理」这个角色的人**：【提交】后进异常，提示写的是「节点「部门审批」在发起人所在部门没有可用的审批人」，不是笼统的「没有可用的审批人」。可【重试】、可【撤回】。
19. **关掉启用流程**：新填的【请假单】底部回到【保存】，【保存】即入库、状态列显示「已通过」，详情里写「流程停用期间保存，没有审批记录」；这批数据在别的表的选记录弹窗里**能挑到**。上一张还在审批的继续审完。**关掉期间三个待办入口照常工作**：首页和应用内的【我的待办】/【我发起的】/【我处理的】仍列出【请假单】的在途单据，审批人照样能【通过】、【驳回】，发起人照样能【撤回】。不能因为「这张表的流程关掉了」就把在途单据从待办里藏起来。
20. **普通表单转为流程表单**：表单树菜单点【转为流程表单】，确认框写清「已有的 N 条数据将记为已通过，且发布流程之前不能再填报」。转完后顶栏出现【流程设计】；原来那 N 条数据状态列是「已通过」、详情里写「转为流程表单之前保存，没有审批记录」；别的表的选记录弹窗**仍能挑到它们**。发布流程之前不能填（同第 2 条）。
21. **流程表单不能转回普通**：【请假单】（已是流程表单）的表单树菜单里**没有**「转为普通表单」。直接调接口想改回普通，被拒绝。建错了只能删表再建。
22. **没有使用权的审批人打开抽屉**：下拉单选、字典字段显示的是「事假」这样的**中文标签**，不是 code 或空白；标签页顺序、子表行都能正常渲染；节点若允许改「选择数据」，弹窗能列出源表已通过的记录。这些都走 `/api/workflow/...`。他看不到【请假单】的【数据管理】，直接调 `records/query` 当作应用不存在，也翻不到别的行。
23. **发起人被移出【使用范围】**：首页【我的应用】里【人事】消失，改网址进来提示「应用不存在」；但首页【我发起的】里那张审批中的【请假单】还在，能打开、能【撤回】、能改完再【再次提交】、异常时能【重试】。已通过的那条只读，改不了（进不了【数据管理】）。
24. **会签里两个人都改了可编辑字段**：A 点【通过】后再看这条数据，A 改的值已经存住；B 点【通过】后 B 改的也存住（同一字段则 B 覆盖 A）。不是只有最后一个人【通过】时才写。
25. **绕过前端直接调接口【提交】**（不带前端校验，主表必填字段空着）：【添加数据】那条、首页【我发起的】里点【再次提交】那条，都要被服务端拦住并返回是哪个字段没填，不产生一条审批人看不全的单据。失权发起人只能调首页那条，同样要拦。
26. **审批人把可编辑的唯一字段改成别人的值**：提示重复，【通过】失败；改回原值或改成没被占用的值才能【通过】。整条【请假单】的流水号从头到尾不变。
27. **删掉一条草稿**：【表单发布】里【删除】开着，在【数据管理】里点【删除】→ 列表没有了，首页【我发起的】里也没有了，MySQL 里对应的实例行一并消失，不留孤儿实例。首页【我发起的】抽屉里没有【删除】。发起人被移出【使用范围】后，首页也删不掉这条草稿。
28. **【撤回】与【通过】同时点**：只有一个人成功。审批人先成功则发起人看到「审批人已开始处理，不能撤回」；发起人先成功则审批人看到「这条待办已处理」。不能两边都提示成功。
29. **已通过后改数据**：发起人 A 在首页【我发起的】打开已通过的【请假单】，只能看，没有【提交】。A 进【请假单】的【数据管理】（【表单发布】里【编辑】开着），改事由后点【提交】→ 状态变回审批中，按**当前已发布**的流程图走，部门经理重新收到待办；别的表选【请假单】的弹窗暂时看不到这条。【表单发布】里【编辑】关着则【数据管理】里没有【编辑】。同一张表里 B（能进【数据管理】、但不是发起人）打开 A 的已通过记录，只能看，没有【编辑】。

## 22. 已经定下来的默认

下面这些都已拍板，按「能落地、和现有习惯接近」选定。若要改，改本文再实现，不要实现时另解释一套。

| 问题 | 定论 |
|---|---|
| 表单类型什么时候定 | **建表时**在「新建表单」对话框里选「普通表单 / 流程表单」；写进 `app_form` 的类型列，判断一律看这一列，不看有没有已发布的流程（§4.1） |
| 流程表单还没配好流程能不能填 | 不能。添加数据页常驻提示，「保存草稿」和「提交」都提示「这张表单还没有配置流程」，服务端也拦，**不写任何记录**（§4.1、§8.2） |
| 类型能不能改 | **只能普通 → 流程**。已有记录一次性回填为「已通过」（不建实例）。流程表单不能转回普通，菜单里没有这项，接口也拒（§4.2） |
| 发布后是否启用 | **已拍板**：发布成功即自动启用。保存草稿只存画布，不启用。一张表同一时刻只有一份正在启用的流程配置 |
| 回填后别的表能不能挑到这些老记录 | 能。回填之后，流程表单上的每条记录都有流程状态，「选记录」弹窗按「已通过」过滤即可，不需要给「没有流程状态」开特例（§15.2） |
| 关掉启用流程期间的保存 | 按普通表单保存，但流程状态记为「已通过」，不建实例；在途单据照常走完，三个待办入口照常列出（§4.3） |
| 草稿要不要过必填 | 要，和现在保存一样 |
| 多人审批 | 或签、会签；节点属性里单选，默认或签 |
| 会签里可编辑字段什么时候写回 | 每个人通过时立刻写回，不等最后一人 |
| 驳回后从哪重新走 | 从开始重新沿连线走（用新数据重新判断分支），用钉死的旧版本 |
| 已通过后还要改 | **已拍板**：只有原发起人能在数据管理里改（发布页「编辑」开着），别人只能看。「我发起的」里只读。改完用**当前已发布**版本重新审批。关掉启用流程期间仍直接保存为已通过（§4.3、§11） |
| 草稿 / 已驳回谁能改能删 | **已拍板**：只有原发起人。别人（含所有者、配置成员）只能看。删除还要发布页「删除」开着，只走数据管理 |
| 选记录弹窗 | 流程表只出已通过 |
| 下拉其他表数据 | 不过滤流程状态 |
| 流程设计器 | 画布：拖节点、拉连线、分支配条件（LogicFlow 2.x） |
| 分支怎么选路 | 只走一条；按线的顺序匹配，否则走「其他情况」 |
| 并行两条同时批 | 不做 |
| 部门主管 / 多级上报 | 不做（组织里没有部门负责人） |
| 「指定角色」审批人跨部门错派 | 解析时**默认限定与发起人同部门**；节点属性里给「限定与发起人同部门」勾选框，默认勾上。取消勾选时明确提示「该角色下所有部门的人都会收到待办」（§7.1、§7.3） |
| 待办入口 | 首页跨应用 + 应用内（应用名下、搜索/新建上，只查本应用）；同一套卡片和抽屉；表单工作台不加页签 |
| 审批人不必有应用使用权 | 是；待办抽屉全部走 `/api/workflow/...`（权限规格 §8.2） |
| 待办抽屉读和写走哪 | **已拍板**：全部走 `/api/workflow/...`。打开一次带齐结构、字典、本条数据、文件回显；选记录 / 联动 / 上传走 `render/:instanceId`。`/apps/:appId/...` 不为待办开例外，也不给待办开放 `PATCH /records`。复用详情抽屉前先抽数据源 |
| 发起人调 render 写入 | **已拍板**：只在草稿 / 已驳回 / 异常时能选记录、上传；审批中、已通过只读 |
| 记录删了、实例还在 | **已拍板**：三个列表卡片标「数据已删除」，只读。草稿删干净（实例+任务一起删） |
| 联动写到只读目标 | **已拍板**：只写本节点可编辑的目标字段；只读、隐藏的不动 |
| 失去使用权的发起人 | 只能在首页操作在途单据，进不了应用、改不了已通过的数据；**不能在首页删草稿**（首页没有删除入口）（权限规格 §8.1） |
| 草稿怎么删 | **已拍板**：发布页「删除」开着才能删，只走数据管理。首页「我发起的」没有删除入口。失权后也不能在首页删 |
| 主表必填由谁校验 | 前端照旧，**提交意图的请求后端也要校验**（现有后端只校验子表列必填、唯一、流水号）。工作台和首页「我发起的」再交都要拦（§8.2、§17） |
| 草稿 / 已驳回从哪保存 | **已拍板**：两扇门、一间库房。工作台 / 数据管理走 records + `intent`；首页「我发起的」走流程实例接口。鉴权分路，保存同一套，引擎只在保存成功后动。不要在流程接口里直接写 Mongo，也不要给失权发起人开放应用 records |
| 内联编辑、导入模版 | 流程表单整表关闭；内联编辑要新加整表判断（现有只看字段级） |
| 历史用不用单独的历史表 | 不用，任务表当历史 |
| 「我发起的」列不列异常 | **已拍板**：列。点开可以重试（发起人在首页就能点；有配置权且能进应用的人也可以点）。审批人不能点 |
| 异常单据谁能点「重试」 | **已拍板**：以权限规格 §12 为准。发起人；能进应用的所有者 / 配置成员。审批人和系统管理员不能点。不要写成「管理员」 |

## 23. 和 TODO、其它文档的关系

- 做完第 1 期后，`docs/TODO.md` P5「流程表单」可勾选，并注明第 2 期另立项。
- **流程第 1 期必须和权限规格第 1 期一起做**：三个待办入口、待办抽屉全部走 `/api/workflow/...`（权限规格 §8.2）、`AppAccessService` 取代 `requireOwnedApp`（权限规格 §12.1）。少了这些，没有使用权的审批人打不开抽屉，流程等于不能用。
- **权限规格第 2 期（配置名单、使用范围、移交）不阻塞流程**：没做之前应用仍只有所有者能进，审批人只走首页。
- P7 数据权限、应用配置 / 使用范围仍是流程之外的平台能力；按表收权是权限规格第 3 期。
- 改这两份规格的规则时**先改文档再改代码**，两份文档说同一件事必须一致（待办入口、授权、页面名、分期、已通过后只能在数据管理里改并重新审批、首页再存与工作台同一套保存）。
- 按项目规则（`AGENTS.md`），流程是新能力、又改变了填报 / 数据管理 / 选记录这些用户可测行为，**同一轮**要更新 `docs/testcases/`（专项文件 + 组合用例 + README）和 `docs/guides/`，不要只留规格。§21 的验收项可以直接当用例骨架。
