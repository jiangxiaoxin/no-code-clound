# 审批节点扩展操作（转交、加签、退回）需求设计

日期：2026-09-07  
状态：已定稿  
范围：审批待办默认就有 **同意**、**驳回**、**退回至上一审批节点**、**退回至发起人**。**转交**、**加签** 在流程设计右侧按节点单独开关，默认关闭。  
相关：

- 流程表单主规格：`docs/superpowers/specs/2026-09-05-workflow-form-design.md`（本文补充 §9 驳回之外的操作；**不**把退回至发起人做成 `rejected` 后再提交）
- 流程版本：`docs/superpowers/specs/2026-09-07-workflow-version-design.md`
- 组织与角色：`docs/superpowers/specs/2026-08-22-admin-organization-rbac-design.md`

## 1. 一句话说清

审批人在 **我的待办** 打开单据时，默认有 **同意**、**驳回**、**退回至上一审批节点**、**退回至发起人**。右侧勾了才出现 **转交**、**加签**。

**转交、加签、两种退回** 都不结束流程，单据状态仍是 **审批中**。只有 **驳回** 才会变成 **已驳回**。

---

## 2. 和现有「驳回」怎么分

| 操作 | 列表里状态 | 主要入口 | 审批人 / 发起人意图 |
|---|---|---|---|
| **驳回** | **已驳回** | 发起人打开 **我发起的** | 不通过，这一轮结束，流程终止；默认可以改单后 **再次提交**，从头审。开始节点关掉「流程终止后是否可以修改后重新提交」后不能再改再交 |
| **退回至上一审批节点** | **审批中** | 上一节点的人在 **我的待办** | 请上一级补批或改字段，**同意后从该节点继续往后** |
| **退回至发起人** | **审批中** | 发起人在 **我的待办** | 请发起人改表单，**提交后从流程开始继续往后** |
| **转交** | **审批中** | 被转交的人在 **我的待办** | 当前节点换一个人处理 |
| **加签** | **审批中** | 被加签的人在 **我的待办** | 当前节点多一个人一起批 |

退回至发起人 **不要** 做成「变成已驳回 + 在我发起的里再提交」——那样和驳回在发起人侧几乎一样，用户分不清「不通过」和「请修改后继续审」。

---

## 3. 要不要新的流程状态

**不要。** 实例顶层状态仍只有：`草稿`、`审批中`、`已通过`、`已驳回`、`异常`。

- 转交、加签、退回至上一审批节点、退回至发起人：全程 **`审批中`**
- 数据管理、我发起的、待办卡片上的流程状态筛选 **不必** 增加「已退回」「已转交」等第六种状态
- 退回、转交、加签的详情写在 **审批进度时间线** 和任务历史上，必要时卡片摘要可带一句「待发起人修改」之类，但状态码仍是 `running`

---

## 4. 流程设计：审批节点上配什么

点画布上的 **审批** 节点，右侧 **「审批操作」** 只配两项，**保存 / 保存并启用** 时写入该节点快照：

| 配置项 | 含义 | 默认 |
|---|---|---|
| 允许转交 | 运行时待办抽屉出现【转交】 | **关** |
| 允许加签 | 运行时待办抽屉出现【加签】 | **关** |

**同意**、**驳回**、**退回至上一审批节点**、**退回至发起人** 不用配，每个审批节点都有。当前是这条线上第一个审批节点时，【退回至上一审批节点】不出现（没有可退的人）。

说明：

- 只对 **`approve` 节点** 生效；开始、分支、结束节点没有这块配置。
- 转交 / 加签随 **实例快照里的图** 走；在途单不随设计器后来改开关而变。
- **启用中** 的版本只读，改开关要先在 **设计中** 的版本里改并 **保存并启用**（或启用新版本），只影响 **新提交** 的单。

---

## 5. 运行时：按钮什么时候出现

在 **我的待办** 打开待办抽屉（与现有通过、驳回同一位置）：

1. 仅 **`kind = todo`** 且当前用户有一条 **`pending`** 待办时，才出现这些按钮。
2. **转交**、**加签** 还要当前审批节点上对应开关为 **开**。
3. **退回至上一审批节点** 若前面没有别的审批节点，按钮隐藏。
4. **我发起的**、**我处理的** 抽屉 **不出现** 这些审批按钮（发起人被退回后的待办见 §9，走待办而非我发起的）。

【同意】【驳回】与两种退回并列；是否必填审批意见的规则 **只作用于同意、驳回**，转交 / 加签 / 退回是否必填意见在 §6～§9 各节单独约定（默认 **退回两类必填意见**，转交 / 加签 **选填**）。

## 6. 转交

### 6.1 界面

1. 点 **【转交】** → 弹出可拖拽对话框 **「转交给谁」**。
2. 用与表单 **人员单选** 类似的选人组件（组织树 + 人员列表），**只能选一名** 启用中的用户。
3. 可选填转交说明；点 **确定** 后关闭抽屉并刷新列表（与通过、驳回成功后行为一致）。

### 6.2 行为

- 实例仍为 **审批中**；**当前节点不变**（`current_node_key` 仍是本节点）。
- **当前操作者** 本条 `pending` 待办变为 **已处理**，动作为 **转交**，意见里可记转交说明；取消原因或等价字段记「已转交」。
- 给 **被选中的一人** 在本节点、**同一轮**（`round`）新建一条 **`pending`** 待办（若该人本轮本节点已有未取消的待办，则不允许转交，提示「该用户已有待办」）。
- **或签**：转交后通常只保留被转交者一条待办（转交者自己的待办结束）；原节点其他 `pending` 是否一并取消，与 **或签下「一人通过取消他人」** 规则一致——**转交不算通过**，不因此取消其他人，除非规格另有「转交后仅保留被转交者」的明确产品决定；**本期采用：只结束转交者本人待办，其余 pending 保留**（与「加签增人」不同）。
- **会签**：转交只替换 **转交者本人** 这一席；其他会签人的待办不动。
- 转交 **不** 写回审批人在表单里改的可编辑字段（与驳回一致：未点通过就不落库那些改动）。

### 6.3 不能转交给谁

- 停用用户、不存在用户。
- 转交给自己（提示「不能转交给自己」）。

---

## 7. 加签

### 7.1 界面

1. 点 **【加签】** → 对话框 **「加签给谁」**，可选 **一名或多名** 启用用户（人员多选交互）。
2. 可选填说明；确定后关闭抽屉。

### 7.2 行为

- 实例 **审批中**；**当前节点不变**。
- **加签者** 在本节点、当前 `round` 新增 **`pending`** 待办（已存在同节点同轮同人的 pending 则跳过或提示，不重复插入）。
- **操作者** 自己的待办 **仍为 pending**（加签不等于通过，除非产品另有「加签并同意」——**本期不做**，加签后操作者仍需自己点通过或驳回）。
- **或签 / 会签** 下加签人都按 **当前节点的 `signMode`** 参与：或签仍是一人通过即可往下；会签仍须全部通过。加签只增加待办人数，不改变 signMode。
- 加签 **不** 写回表单未通过前的编辑内容。

---

## 8. 退回上一节点

### 8.1 界面

1. 点 **【退回上一节点】** → 对话框要求填写 **退回意见**（**必填**）。
2. 确认后关闭抽屉。

### 8.2 「上一节点」指什么

按 **本实例当前这一轮** 已经走过的路径算，不是图上随便找一条入边：

1. 取实例 **`visited_node_keys`** 里出现过的 **审批节点**，按实际经过顺序排列。
2. **上一节点** = 当前待办所在审批节点之前、**最近的一个审批节点**。
3. 若当前就在 **第一个审批节点**（前面没有别的审批节点），**不允许** 退回上一节点，提示「没有上一审批节点」。

有 **分支** 时：以 **实例实际走过的** 审批节点序为准，保证退回到「来时的上一站」，而不是图上别的岔路的节点。

### 8.3 行为（与 §10 统一的「退回」逻辑）

1. 实例保持 **审批中**。
2. **当前节点** 及 **之后** 在本轮尚未结束的 `pending` 待办全部 **取消**，取消原因记「退回至「xxx」」之类。
3. 当前操作者本条待办记 **已处理**，动作为 **退回上一节点**，意见为填写的退回意见。
4. **`round` + 1**（整单进入新一轮，避免与上一轮已「通过」的任务冲突；历史任务仍保留在进度里）。
5. **`current_node_key`** 设为 **上一审批节点**；**`visited_node_keys`** 截断到 **不包含** 当前节点及之后（小流程图「本轮路径」从上一节点重新高亮）。
6. 在 **上一节点** 重新派 **`pending`** 待办：
   - **本期：上一节点当时是谁批的，退回后就仍派给那些人**（同一 `round` 下看上一轮该节点 **已完成 `approve` 的任务** 的 `assignee`；若该节点是会签，则 **所有当时通过的人** 都要重新收到待办）。
   - 若上一节点当时解析出的审批人里有 **已停用** 账号：跳过停用者；若 **无人可派**，实例进 **异常**，原因写清「退回后节点「xxx」没有可用的审批人」，与现有「无人可派进异常」一致。
7. 上一节点的人在 **我的待办** 打开后：
   - 表单字段按 **上一节点** 的 **字段权限**（可编辑 / 只读 / 不可见）展示；
   - 可改 **审批意见**（新一条，不覆盖旧进度）；
   - 点 **通过** 后写回该节点允许编辑的字段，再 **沿流程图继续往后**（下一节点可能是刚才退回前的节点，需重新派待办）。
8. 退回 **不** 写回当前节点操作者尚未点通过时在表单里改的内容。

### 8.4 和打回发起人的区别（即使同一个人）

若 **上一节点审批人** 恰好是 **发起人**：

- **退回上一节点**：待办挂在 **上一审批节点** 上，走 **审批节点字段权限**，底部是 **通过 / 驳回**（及本节点开启的转交等）。
- **打回发起人**：待办挂在 **发起人任务** 上（§9），表单可改范围按 **发起提交**，底部是 **提交**，不是通过 / 驳回。

**不因是同一个人就合并成一个按钮。**

## 9. 打回发起人

### 9.1 界面

1. 点 **【打回发起人】** → 对话框 **退回意见必填**。
2. 确认后关闭抽屉。

### 9.2 行为

1. 实例保持 **审批中**（**不是** 已驳回，**不是** 草稿）。
2. 取消当前及之后所有 **`pending`** 待办；当前操作者待办记 **已处理**，动作为 **打回发起人**。
3. **`round` + 1**。
4. **`current_node_key`** 设为特殊值 **`start`**（表示流程停在「待发起人处理」；开始节点本身不是审批节点）。
5. **`visited_node_keys`** 清空或仅保留开始（小流程图：尚未进入本轮审批节点，或高亮「待发起人提交」——界面实现时与 §9.4 一致即可）。
6. 给 **发起人** 派一条 **`pending`** 待办：
   - **`node_key = start`**
   - **`assignee_id = 发起人`**
   - 任务类型为 **发起人待办**（不是普通审批待办）。
7. 发起人在 **我的待办**（**不是** 我发起的）打开：
   - 表单字段：**整单按发起提交规则可改**（等同工作台添加数据 / 提交时的可编辑范围，**不** 套用某一审批节点的 fieldAccess）；
   - 底部主按钮：**【提交】**（不要显示通过、驳回）；
   - 可选 **【保存】** 是否支持：若支持，只更新 Mongo 业务数据，**不** 推进流程、不改变待办状态；若不支持，仅保留提交——**本期建议：只提供【提交】，不提供单独保存**（简化）。
8. 发起人点 **【提交】**：
   - 跑与 **首次提交 / 再次提交** 相同的主表必填、子表、唯一性等校验；
   - 更新 Mongo 数据；
   - 本条发起人待办 **完成**，动作为 **重新提交**（或等价命名）；
   - 从 **开始** 节点 **advance**，按快照图重新走（分支重新算），**不** 经过 `rejected` 状态。
9. 打回 **不** 写回当前审批人未通过前的表单改动。

### 9.3 和驳回、撤回的区别

| | 打回发起人 | 驳回 | 发起人撤回 |
|---|---|---|---|
| 状态 | 审批中 | 已驳回 | 草稿 |
| 发起人入口 | **我的待办** | 我发起的 | 我发起的 |
| 谁触发 | 审批人 | 审批人 | 发起人 |
| 语义 | 请修改后继续 | 不通过 | 我不交了 |

### 9.4 小流程图与进度

- 打回后进度里写：`李四 打回至发起人修改：xxx`。
- 发起人提交后写：`张三 已重新提交`。
- 小流程图在发起人待办期间：可不高亮任何审批节点，或高亮 **开始**；提交后再按实际路径高亮。

## 10. 两种退回的公共规则（摘要）

| 步骤 | 说明 |
|---|---|
| 状态 | 始终 **审批中** |
| 待办入口 | **我的待办** |
| 意见 | **必填**（转交、加签默认选填） |
| 轮次 | **`round + 1`** |
| 当前节点待办 | 取消 + 记录操作 |
| 目标 | 上一审批节点 **或** 发起人（`start`） |
| 表单改动 | 未「通过 / 提交」前的不落库 |

引擎层可统一为一个 **退回** 能力，参数为 `target: previous | start`，避免两套分叉逻辑。

## 11. 与或签、会签的关系

| 场景 | 规则 |
|---|---|
| 或签下有人点 **退回** | 同节点其余 **pending** 取消（与「一人驳回取消他人」类似，但实例 **不进已驳回**） |
| 会签下有人点 **退回** | 同节点其余 **pending** 取消；上一节点重派时 **会签原参与者全员** 重批（§8.3） |
| 或签下 **转交** | 仅结束转交者本人待办；其他人 pending 保留（§6.2） |
| 会签下 **加签** | 增加 pending；仍须满足会签全部通过才往下 |

## 12. 审批进度与「我处理的」

`WorkflowProgressList`（流程页签时间线）应展示：

- 转交：`时间 · 张三 · 部门审批 · 转交给李四 · 意见`
- 加签：`时间 · 张三 · 部门审批 · 加签王五 · 意见`
- 退回上一节点：`时间 · 李四 · 人事备案 · 退回至「部门审批」 · 意见`
- 打回发起人：`时间 · 李四 · 人事备案 · 打回至发起人修改 · 意见`
- 发起人重新提交：`时间 · 张三 · 已重新提交`

从上到下按事情发生的先后排。加签后：先出现加签说明，再是被加签人的「待处理」。或签里先加签再驳回时：先出现加签说明，再是本人驳回，最后才是其他人「未处理（已取消）」。不要因为被加签人的待办建得早就插到加签说明或驳回前面。

**我处理的** 里操作者完成转交 / 加签 / 退回后，卡片进入 **我处理的**，与通过、驳回一致。

## 13. 数据与接口（实现参考，界面语言优先）

以下为开发对照，产品读 §4～§12 即可。

### 13.1 节点快照（审批节点上新增字段）

在现有 `approver`、`signMode`、`fieldAccess` 等旁增加布尔字段（命名示例）：

- `allowTransfer`
- `allowAddSign`
- `allowReturnPrevious`
- `allowReturnStart`

默认值见 §4 表。

### 13.2 任务动作扩展

在现有 `approve`、`reject` 外增加，例如：

- `transfer`（转交）
- `addSign`（加签）
- `returnPrevious`（退回上一节点）
- `returnStart`（打回发起人）
- `resubmit`（发起人待办上的提交）

任务仍用 `pending` / `done` / `cancelled`；**不需要** 新任务状态枚举。

### 13.3 发起人待办

- `node_key = 'start'` 的 `pending` 任务表示 **待发起人提交**。
- 待办详情接口对这类任务返回：`canResubmit: true`，`canApprove / canReject: false`，且不返回审批节点 `fieldAccess`（前端按发起编辑规则展示）。

### 13.4 接口草案

| 人做的事 | 方法与路径（草案） |
|---|---|
| 转交 | `POST /api/workflow/tasks/:taskId/transfer`，body：`{ assigneeId, comment? }` |
| 加签 | `POST /api/workflow/tasks/:taskId/add-sign`，body：`{ assigneeIds[], comment? }` |
| 退回上一节点 | `POST /api/workflow/tasks/:taskId/return-previous`，body：`{ comment }` |
| 打回发起人 | `POST /api/workflow/tasks/:taskId/return-start`，body：`{ comment }` |
| 发起人待办提交 | `POST /api/workflow/tasks/:taskId/resubmit`，body：`{ data }`（校验与 instances submit 一致） |

打开待办详情时，除现有 `canApprove`、`canReject` 外，增加 `canTransfer`、`canAddSign`、`canReturnPrevious`、`canReturnStart`、`canResubmit`（由节点配置 + 任务类型 + 是否有可退目标共同决定）。

## 14. 异常与边界

| 情况 | 处理 |
|---|---|
| 退回 / 打回后重派时审批人为空 | 实例 **异常**，`errorReason` 写清节点名与原因；发起人 / 配置者可 **重试**（沿用 §16.5） |
| 转交 / 加签选中停用用户 | 前端选人列表不展示或确定前校验拦截 |
| 并发：两人同时退回 | 与通过、驳回相同，用「待办 id + pending + assignee」条件更新，失败则提示已处理 |
| 当前节点是唯一审批节点 | **退回至上一审批节点** 不出现；**退回至发起人** 仍有 |
| 实例已异常 / 已驳回 / 已通过 | 不允许转交、加签、退回 |

## 15. 本期不做

- 退回到 **任意指定节点**（只能上一节点或发起人）
- **减签**（加签后再移除某人）

## 17. 验收场景（简要）

用 **请假单**（事假 → 部门审批 → 人事备案）：

1. 人事备案点 **退回至上一审批节点**：退回到部门审批，张三在 **待办** 里改事由后同意，流程回到人事备案。
2. 人事备案点 **退回至发起人**：发起人在 **待办**（非我发起的）改日期点 **提交**，状态全程 **审批中**，再次经过部门审批。
3. 同一张单：张三既是发起人又是部门审批人——分别测两种退回，确认按钮、字段可改范围、底部按钮不同。
4. 部门审批开启 **转交**：转交后仅被转交者有待办（转交者待办结束），同意后流程继续。
5. 部门审批开启 **加签** 且 **会签**：加签后须全部同意才进人事备案。
6. **驳回** 仍为 **已驳回**，与退回至发起人在状态和入口上可区分。

## 18. 拍板结论

1. 转交、加签、两种退回：**不新增** 顶层流程状态，全程 **审批中**（除驳回外）。
2. 退回至发起人：**审批中 + 发起人我的待办 + 提交**，**不是** 已驳回后再提交。
3. 两种退回：**同一套退回引擎**，目标不同；**不因处理人相同而合并按钮**。
4. 默认就有：**同意**、**驳回**、**退回至上一审批节点**、**退回至发起人**。右侧只配 **转交**、**加签**，默认关。
5. 退回类操作 **必填意见**；转交、加签意见 **选填**。
6. 退回后 **`round + 1`**；上一节点重派 **原审批人（会签全员重批）**。
