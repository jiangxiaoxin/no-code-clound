## 1. 一句话说清

现在：**一个应用默认只有创建它的人能看见、能用、能改。** 管理后台的角色只管人、部门、角色，管不到应用。

以后应用上分三件不同的事：

1. **所有者**：永远只有一个人。刚创建时就是创建人。可以交给别人，交出后自己不再能配置。
2. **配置**：改表单、改流程、进应用后台、改权限。默认只有所有者。可以再点名加上几个人——选的时候可以用部门、角色帮忙找人，**存下来的只有这些人**，不是整个部门或角色都能配。**能配置的人同时可以使用应用**（填表、数据管理），不必再写进使用范围。配置权限页上**始终列出所有者本人**（标「所有者」、不能移除），这样「名单上有谁 = 谁能配置」，不会出现名单里看不到所有者、他却能配置的情况。
3. **使用**：进应用、填表、看数据管理。默认只有所有者和配置名单上的人。还可以在应用后台「使用范围」里向外开放，按部门、角色、人员划定范围；范围内的人首页能看到这个应用（只有使用、不能配置）。使用范围页顶部同样固定显示一块「始终可用（不可移除）」，列出所有者和配置名单上的人。

被派了待办的人**不必有使用权限**，在首页「我的待办」也能看到并处理**那一条**。

**不要**做成「组织角色上勾了就能进所有应用」。组织角色只当选人、划使用范围、流程里指定审批人的标签。

## 2. 现在系统里已经有什么

打开管理后台 → 角色，能勾的是：进入管理后台、查看/新建人员、部门、角色等。登录后顶栏头像菜单里出现「管理后台」，靠的是 `admin.access`。

首页「我的应用」只列出 `ownerId = 当前用户` 的应用。点进应用、改表单、填数据、管字典，接口都先查「当前用户是不是这个应用的创建人」，不是就当应用不存在。

表单发布页已有整张表的开关：新增、编辑、删除、导入等。这些开关回答「这张表允不允许这种操作」，**不回答「哪个人可以」**。现在能进应用的只有创建人，所以开关等于只约束创建人自己。

流程还没上线。流程规格已经定：审批走首页和应用内「我的待办」，打开某一条靠任务，不靠是不是所有者。

## 3. 几层各管什么（不要混）

| 层 | 人怎么理解 | 配在哪 | 现在 |
|---|---|---|---|
| 组织 | 能不能进管理后台、改人、改部门 | 管理后台 → 角色 | 已有 |
| 应用所有者 | 这个应用归谁，永远一个人 | 应用表上的所有者；应用后台可移交；所有者停用后改走管理后台，仅系统管理员能交 | 创建人 = 所有者 |
| 应用配置 | 谁能改这个应用（设计、后台、权限） | 应用后台 → 配置权限 | 只有创建人 |
| 应用使用 | 谁能在首页看见并进这个应用用表单 | 应用后台 → 使用范围 | 只有创建人 |
| 表单发布开关 | 这张表允不允许新增 / 编辑 / 删除 / 导入 | 表单设计顶栏「表单发布」 | **现在就有，本期继续生效** |
| 按表「谁可以」/ 行范围 | 进了应用后，哪个人能填这张表、能看哪些行 | 以后按表再收（§10） | 能进就能用全部表 |
| 流程例外 | 没使用权也能打开**这一条**待办 | **不属于任何应用权限层**：不配权限表，按任务和发起人授权 | 跟流程一起做 |

另外两套**不要**并进上面任何一层：

- **表单发布开关**：整表关了「删除」，有使用权的人也没有删除按钮。
- **流程节点字段权限**：审批抽屉里字段可编辑 / 只读 / 隐藏。只在流程设计里配，见流程规格 §12。

「菜单权限」不另做一张配置表。首页有没有这个应用，看使用范围（加上所有者、配置名单上的人）；应用里有没有「表单设计 / 应用后台」，看是不是所有者或在配置名单里。

## 4. 组织权限（已有，本文不改规则）

继续按 `2026-08-22-admin-organization-rbac-design.md`：

- 一人一个部门（没有兼任）。
- 一人多个角色，权限取并集。
- 角色停用、人员停用，下一次请求就失效。
- JWT 里不存最终权限码。

**管理后台管理员 ≠ 看见所有应用。** 能管人，不表示能打开别人的「设备台账」。要使用某个应用，必须在该应用的使用范围内（或是所有者 / 配置名单上的人）。唯一例外见 §5.2：系统管理员可以在管理后台把「所有者已停用」的应用交给别人，**只做移交**，仍然打不开这个应用、看不到里面的表和数据。

组织角色在应用里的用途：

- **配置权限**：用角色当选人器，勾出具体人再添加。
- **使用范围**：可以直接挂上一个角色，该角色下的人都能用。新加进角色的人也能用
- **流程审批人**：仍按流程规格选组织角色。

**不要**在组织角色上勾「某某应用配置权」。（应用的配置权是按人来划分的，只有个别的人有配置的权限）

## 5. 所有者（永远一个人）

应用表上的 `ownerId` 就是所有者。刚点「新建应用」时，当前登录人是所有者。

所有者永远只有 **1** 个人。没有「共同所有者」，也不再用「管理员」这种身份代替所有者。

所有者默认同时有：

- **配置**：设计表单和流程、表单发布、应用后台（字典、配置权限、使用范围）、改应用名、新建/删分组和表单、**删除表单**、删除应用、移交所有者。
- **使用**：首页能看见、能进应用、能用表单。

不能把所有者从使用范围里拿掉——人还是所有者，就一定能进。要从使用变成普通人：走 **移交**。

### 5.1 移交

应用后台提供「移交所有者」。只有**当前所有者**能点。

选一个启用中的人（不能选自己）→ 确认后：

1. 所有者改成这个人。
2. 原来的所有者**失去全部配置权**，变成**普通使用用户**。系统在「使用范围」里补一条「人员 = 旧所有者」（已经有则不重复加），所以他首页还能看到这个应用、还能进、还能填。配置权限页名单第一行已经变成新所有者（标「所有者」），旧所有者不在名单里——除非后来有配置权的人又把他当普通人加进配置。
3. 当前这个人正在应用后台点移交，确认后立刻不能再待在后台——**跳到项目首页**。他要再用这个应用，从首页「我的应用」点进去即可（此时只是普通使用，打不开表单设计、应用后台）。
4. **有配置权的人**若要把旧所有者踢出去，到「使用范围」里把他从范围中移除（或去掉覆盖他的部门/角色）。移除之后，旧所有者首页不再出现这个应用，也不能再进。不限于新所有者本人——名单上其他人同样能改使用范围。
5. **移除使用权不影响他已经发起的单据**：旧所有者作为发起人的在途单据（草稿、审批中、已驳回、异常），仍然能在首页「我发起的」里打开、修改、保存草稿、再次提交、撤回、重试。他**不能**因此重新进入应用，也进不了该表的数据管理。详见 §8.1。

新所有者立刻拥有配置和使用。配置名单表里存的是「额外能配的人」，**不含当前所有者、也不含刚交出去的旧所有者**（**方案 A**）：

- 打开配置权限页时，把当前所有者合并成第一行（见 §6.2、§11）。界面上只有一行「所有者」，不要再留一行普通成员。
- 若新所有者移交前就在名单里，**删掉他那一行**。身份靠 `ownerId`，不要靠名单行。
- 若新所有者移交前有一条「人员 = 他」的使用范围，**删掉那一条**（他已在「始终可用」里）。
- 不要给旧所有者加名单行——他已经是普通人，只靠自动补的使用范围。
- **他以后再交出去**：升为所有者时那一行已经没了，所以再交给别人之后，他也只是普通人（使用范围再补「人员 = 他」）。不要留着配置行，否则他交出去后还能配，和「失去全部配置权」相反。

管理后台那条移交（§5.2）对名单、使用范围的处理与上面相同。

删除应用：只有所有者可以。配置名单上的人不能删应用，也不能移交。系统管理员按 §5.2 只能移交，不能删应用。

### 5.2 所有者停用后：系统管理员仅做移交

应用里的「移交所有者」只有当前所有者能点。所有者账号一停用，这条路就断了——他登不进去，配置名单上的人也不能替他交。

**出路**：管理后台里、拥有内置「系统管理员」角色（`system_admin`）的人可以移交。只这一件事。

人在哪点：管理后台 → 人员 → 打开这个**已停用**的人 → 若他还是某些应用的所有者，列出这些应用（应用名即可）→ 某一行点「移交」→ 选一个启用中的人 → 确认。所有者还在启用时，这里不出现移交——他自己进应用后台交。

确认后的库表变化和 §5.1 完全一样（改所有者、名单里不留新旧所有者、使用范围补「人员 = 旧所有者」）。旧所有者此时是停用账号，补上的范围行先不生效；以后若再启用，他会以普通使用用户出现，新侧有配置权的人可以再去掉。

**系统管理员仍然不能**：

- 打开这个应用、进表单设计、进数据管理、改配置名单或使用范围
- 删除这个应用
- 在首页「我的应用」里看见它（除非移交对象就是他自己，交完他才变成所有者）

可以交给任何一个启用中的人，包括系统管理员自己。交给自己之前打不开；交给自己之后他就是新所有者，这是换主人的结果，不是移交过程中多出来的查看权。

普通管理后台角色（只有 `admin.access`、没有 `system_admin`）不能做这件事。不要做成「能管人就能交别人的应用」。

## 6. 配置权限（最后落到人）

### 6.1 默认

没在应用后台加过任何人时，**只有所有者能配置**。

### 6.2 人在界面上怎么加

应用后台增加「配置权限」页（和现在的「字典管理」并列）。只有所有者和已经在配置名单里的人进得来。

列表：**所有能配置的人**（姓名），所有者固定第一行并标「所有者」。

- 所有者那一行**没有移除按钮**，旁边一句说明：「所有者始终能配置本应用。要让他失去配置权，请移交所有者。」
- 其余行是额外添加的人，可以移除。
- **没有**「整个部门」「整个角色」两行——存下来的只有人。

点「添加」：和人员选择类似，可以用部门、角色、人员把人找出来，勾选后确定。**写入名单的只有被勾上的那些人。**

- 勾了「研发部」里的张三、李四：名单里是张三、李四。王五后来调进研发部，**不会**自动获得配置权。
- 勾了角色「部门经理」下当前的人：只把当时勾上的人加进去。以后新当上部门经理的人，**不会**自动能配置。
- 不能添加停用人员。
- 勾中的人里包含所有者：不报错、不写重复行，提示「已是所有者，无需添加」。

名单上的人后来被停用：这一行仍在，姓名旁标「已停用」。他自己登不进去，配置权、使用权都立刻没了（平台层拦登录，§12）。**可以删掉这一行**，删掉后名单里不再出现。所有者那一行如果账号停用，同样标「已停用」，仍然没有移除按钮（要换人：所有者自己交，或停用后由系统管理员在管理后台交，见 §5.2）。

移除：只有**有配置权的人**能改这份名单。只能移除普通成员（含已停用的普通成员），**可以移除自己**。所有者那一行始终不能移除。移除时二次确认，文案要说清两个后果——他不能再配置本应用；**如果使用范围也没有覆盖他，他同时失去使用权**，首页不再出现这个应用（§7.1：默认能使用的人就是所有者 + 配置名单上的人）。有人把自己移出、且范围也盖不住自己时，当前页立刻待不下去，回到项目首页。

### 6.3 有配置权的人能做什么

配置权 = 所有者能做的事，**只少两件**：不能移交所有者、不能删除应用。其余全部相同：

- 进应用（首页能看到这个应用，即使没被写进使用范围）。
- 打开表单设计、流程设计、表单发布。
- 进应用后台：字典管理、配置权限、使用范围。
- 改应用名、新建/重命名/删除分组和表单。
- **删除表单**：和所有者一样可以删。现有实现删表单会**连带删掉这张表的全部填报数据**（`server/src/application/application.service.ts:362-374`，`dropFormCollection`），所以删除确认框必须写明「将同时删除该表单已填报的 N 条数据，不可恢复」，不要只写「确定删除这个表单吗」。
- **转换表单类型**（只允许普通 → 流程，流程规格 §4.2）：属于设计级动作，有配置权就能做，不必是所有者。入口在普通表单的表单树节点菜单里。确认框必须写明：已有记录会一次性标成「已通过」（不补审批记录），且发布流程之前不能再填。流程表单**没有**转回普通的入口，接口也拒。
- **使用表单**（【添加数据】、【数据管理】）：**能配置就能使用**，不必再写进使用范围。和第 7 节范围里的人一样能填、能看【数据管理】（再叠加【表单发布】开关）。

## 7. 使用权限（按范围开放）

### 7.1 默认

没配过使用范围时，**只有所有者和配置名单上的人能使用表单**。能配置的人同时就能使用，不用再往使用范围里加一遍自己。

反过来也成立：**从配置名单移除一个人，他就同时失去使用权**——除非使用范围里有覆盖他的部门、角色或人员条目。移除时的确认文案要写清这一点（§6.2）。

### 7.2 人在界面上怎么配

应用后台增加「使用范围」页。**不要叫「发布」**：表单设计顶栏已经有一个「表单发布」（管这张表允许哪些操作），同一个产品里两个「发布」必然被混淆。这一页说明「谁能在首页看到并使用这个应用」。**谁能改这一页：有配置权的人**（所有者或配置名单上的人），不是「只有新所有者」。

页面从上到下两块：

1. **始终可用（不可移除）**：只读区块，列出所有者和配置名单上的人（灰底、没有移除按钮），一句说明「这些人因为身份始终可以使用本应用，不需要写进下面的范围」。其中后来停用的人标「已停用」（和配置权限页同一套）。存储上**不落范围行**，读取时合并出来（§11），理由与配置名单相同：身份一变，展示自动跟着变，不留脏行。
2. **使用范围**：可增删的条目列表，每条是部门 / 角色 / 人员里的一种。

添加范围：选 **部门**、**角色** 或 **人员**。选完保存的就是这条范围，**不是**拆成当时部门里的人。

- 选了「研发部」：研发部里现在的人、以后调进来的人，只要还在这个部门且账号启用，首页就能看到这个应用。**调出部门后下一次请求就进不去**（不用等第二天：现有实现每个请求都重新查库，`server/src/auth/jwt.strategy.ts` 每次调用 `getPrincipal`）。不含下级部门，避免挂上公司根部门等于全员；要含子部门另开规格。界面上选部门时要写明「不含下级部门」。
- 选了角色「部门经理」：当时和以后拥有该启用角色的人都能用。角色停用后，靠这个角色进来的人立刻失去使用。
- 选了人员张三：就是张三。**不能把已经停用的账号加进来。**
- **没分配部门的人**：部门范围盖不住他们。要让他们能用，选一个他们有的角色，或直接按人员把他们加进去。

列表里能看见每条范围（部门名 / 角色名 / 人名），并能移除。

**部门、角色或人员被停用、被删除之后**：范围行**保留但不再命中**（部门/角色恢复启用后自动重新生效，不用重配；人恢复启用后，这条人员范围也重新生效）。页面上把这类条目标出来，并提示去修改或移除，不要让人以为它还开着：

- 停用：`研发部（已停用，当前不生效）`、`部门经理（已停用，当前不生效）`、`张三（已停用，当前不生效）`
- 已删除、还能读到原来的名字：`研发部（已删除，当前不生效）`
- 已删除、名字也读不到：`部门（id:xxxxx，已删除，当前不生效）`、`角色（id:xxxxx，已删除，当前不生效）`
- **人员被删除**：管理后台现在只能停用、没有删人接口。这一项**预留**；当前用「已停用」即可。以后若做删人，再按「人员（id:xxxxx，已删除，当前不生效）」回显。

**加入配置名单、或升为所有者时，删掉他的「人员 = 他」范围行**（有才删）。他已经在「始终可用」里，再留一条人员范围会重复、移交后再交出去时也难算。移交时补给旧所有者的「人员 = 旧所有者」照旧（§5.1）。

移交后的旧所有者：系统自动加一条「人员 = 旧所有者」的使用范围，这样他还能用；**有配置权的人**可以删掉这条（删掉后他在途单据的处理见 §5.1 第 5 步、§8.1）。

**这一页要固定显示一句醒目提示**：在第 3 期按表收权（§10）做完之前，开放范围等于把本应用**所有表的全部数据**开放给范围内的人——他们能进每张表的数据管理看**全部行**。把「请假单」所在应用的使用范围开到全公司，就意味着所有人都能看到彼此的请假事由。

### 7.3 有使用权的人能做什么

- 首页「我的应用」出现这个应用。
- 点得进；左侧有「我的待办 / 我发起的 / 我处理的」、分组和表单树。
- 能用本应用里的表单：【添加数据】、【数据管理】（再叠加【表单发布】开关；流程表单再叠加流程规格）。
- **不能**打开表单设计、流程设计、应用后台（除非同时还在配置名单或是所有者）。
- 第 10 节还没做之前：能进就能用**所有表**，数据管理看**全部行**。

不是所有者、不在配置名单、使用范围也没命中：首页没有这个应用；改网址进来提示「应用不存在」（和现在对非创建人一样）。

## 8. 流程例外：待办不靠应用访问

和需求第 4 条、流程规格 §10 一致：

1. **首页**「我的待办 / 我发起的 / 我处理的」：每个登录的人都能进。列出自己的任务或自己发起的单，**跨应用**。
2. 打开抽屉看到的是**对应那一条**表单数据。不管有没有这个应用的使用权、配置权，只要是这条待办的处理人（或发起人 / 自己批过的），就能看、就能按规则处理。
3. **不要**先查「能不能进应用」。
4. **应用内**左侧同样三行：必须已经能进这个应用（所有者、配置名单或使用范围）；查询带当前应用 id，别的应用的单不能出现。
5. **数据管理仍要有使用权**，分两种人，不要混为一谈：
   - 审批人**没有**本应用使用权：他只能处理这一条。批完不能顺着去翻该表数据管理，也看不到该表其它行。
   - 审批人**同时有**使用权（在配置名单或使用范围内）：他本来就能进数据管理，按 §7.3 在第 3 期之前能看该表**全部行**。这不是流程给的权限，是使用权给的，不要当成流程的漏洞去堵——要收就靠 §10。
6. 通过 / 驳回只从「我的待办」抽屉走。

没有流程、或这张表还不是流程表单：没有这条例外。

### 8.1 发起人失去使用权之后（已拍板）

会出现的场景：移交后有配置权的人把旧所有者移出使用范围（§5.1 第 4 步）；或者某人原来在范围里、发起了单据，后来范围调整把他排除了。

**允许**——在首页「我发起的」打开这条单据，对**在途状态**（草稿、审批中、已驳回、异常）继续操作：修改内容、保存草稿、提交 / 再次提交、撤回、重试异常。流程已经启动，不该因为后来的权限调整把单据掐死在半路。异常重试不只发起人能点：该应用的所有者 / 配置名单上的人也能在应用内点（§12）。审批人和系统管理员不能点。

**不允许**：

- 进入这个应用（首页「我的应用」里没有它，改网址进来提示「应用不存在」）。
- 应用内左侧那三行看不到这些单（人根本进不了应用）；他只能走首页。
- 打开该表的数据管理，或看到该表其它行。
- **修改「已通过」的单据**：
  - **没使用权**：首页「我发起的」里只读，不能改。进不了应用，也就进不了数据管理。
  - **有使用权、且我是原发起人**：也不能在「我发起的」里改。只能进该表**数据管理**改（发布页「编辑」得开着）。改完提交后**重新走审批**，用当前已发布版本（流程规格 §11）。
  - **有使用权、但我不是发起人**：数据管理里也只能看。A 交过的假，B 改不了。
- 删除任何数据，包括自己的草稿。首页「我发起的」**没有删除入口**。草稿要删：必须还能进应用，走该表数据管理，且发布页「删除」开着。失权后这条路也没有。

### 8.2 待办抽屉：读和写都走流程接口（已拍板）

**一条原则**：首页和应用内的「我的待办 / 我发起的 / 我处理的」是同一套抽屉。这里面用到的读和写，**全部**走 `/api/workflow/...`，授权只看「这条任务或这条实例」。有没有这个应用的使用权都一样，不要一半走应用接口、一半走流程接口。

`/apps/:appId/...`（表单结构、字典、`records/query`、上传、普通 PATCH 记录）继续只认「能使用 / 能配置」。**一条都不为待办开例外。** 否则没有使用权的审批人要么打不开，要么整张表被顺手放开。

**打开抽屉（一次带齐、不再向应用接口要）**

`GET /api/workflow/inbox/:kind/:id`（待办 / 已处理用 taskId，我发起的用 instanceId）一次带回：

- 表单结构（字段、控件、标签页顺序）
- 这一条记录的数据（含子表行）
- **该应用的字典项**（下拉才能显示「事假」而不是 code）
- 流程快照（小流程图、当前节点、历史与意见）
- 发起人、审批人的显示名（组织接口登录即可用，也可以夹在这次响应里）
- 本条已经挂上的图片 / 附件的可访问地址（只读回显用）

现有 `getForm`、`apps/:appId/dictionaries`、`FormRecordService` 都按应用鉴权，**不能**直接复用给没有使用权的人。

**抽屉里还要点的（仍按这一条实例授权）**

节点可能把「选择数据 / 关联数据」标成可编辑，联动会带出，图片 / 附件也可能改。这些不能去调应用里的 `records/query` 或上传接口。另开几条挂在同一条实例下的窄接口（路径与流程规格 §17 相同）：

- `POST /api/workflow/render/:instanceId/source-records`
- `POST /api/workflow/render/:instanceId/linkage`
- `POST /api/workflow/render/:instanceId/files`、`GET /api/workflow/render/:instanceId/files/:fileId`

用法：

- 选记录：只查**该字段配的那张源表**，流程源表只出已通过，分页和现有弹窗一样。字段只读时不调这条，标题已经在本条数据里。
- 联动：只按该字段已配好的联动查带出。
- 上传：只有当前这个人在这个抽屉里被允许改这个字段时才能传。
- 回显文件：只能是这条记录上已经挂着的文件。

服务端先确认：当前用户是这条实例的发起人、或这条待办的处理人、或曾经处理过。「我处理的」只读，不要给选记录写入和上传。**发起人只在草稿 / 已驳回 / 异常时能写入和上传**；审批中、已通过只读。

**写**

通过 / 驳回、存草稿、再次提交、撤回、重试，走流程规格 §17 已有的 `/api/workflow/tasks/...`、`/api/workflow/instances/...`。**不要**给待办或失权发起人开放 `PATCH /apps/:appId/forms/:formId/records/:id`。有使用权的人在数据管理里改已通过，仍走应用那条 records 接口（带提交意图），和抽屉不是一条路。

首页「我发起的」再存草稿 / 再次提交：鉴权只认发起人，**保存必须走与应用 records 同一套**（类型转换、必填、子表、唯一、流水号、创建人/更新人），成功后再改实例。不要在流程服务里直接改填报。工作台那条先判「能使用」，再进同一套保存。两扇门，一间库房（流程规格 §17）。

放行粒度始终是「**这一条单据 + 渲染 / 操作它所需的东西**」，不是「这张表」。

| 已有能力 | 叠加上权限之后 |

## 11. 库里怎么存

配置走 MySQL。不要为权限再抄一份用户表。

**表名与实体风格（跟项目现有写法，和流程规格 §15.1 同一套）**：表名是**单数下划线**（`application`、`app_form`、`user_role`），**不是 plural**。列是**驼峰**，TypeORM 不配命名策略，列名就等于属性名（`appId`、`userId`、`createdAt`，对照 `application.ownerId`）。普通索引用 `IDX_表名_属性`，**唯一约束用 `uk_表名_属性`**（对照 `uk_user_department_userId`）。没有公共 BaseEntity，各实体自己声明 `id`、`createdAt`、`updatedAt`。建议表名：配置名单 `app_configurator`，使用范围 `app_access_scope`。

**应用**：现有 `ownerId`，含义改为**所有者**，永远一个人。移交改这一列，同时按下面两段处理配置名单和使用范围（§5.1）。

**配置名单 `app_configurator`**（一个应用多行）：

- 属于哪个应用、**只有用户 id**。没有部门 id、没有角色 id。
- **不存当前所有者，也不在移交时给旧所有者加行。** 名单展示时把当前所有者合并成第一行（§6.2）。
- 移交时：若新所有者原来在名单里，**删掉他那一行**。移交完成后，这张表里既没有旧所有者，也没有新所有者。
- 唯一约束 `uk_app_configurator_appId_userId`。普通索引：`appId`（判定某人能否配置某应用），另加 `userId`（首页反查「我能配置哪些应用」）。

选人时用部门/角色只是界面，确定时把勾中的用户写成这些行。同一人不要重复行；勾中所有者时忽略（§6.2）。

**使用范围 `app_access_scope`**（一个应用多行）：

- 属于哪个应用
- 类型：人员 / 部门 / 组织角色（三种里恰好一种）
- 对应的用户 id / 部门 id / 角色 id
- **不存「始终可用」那些人**（所有者、配置名单上的人）。那一块是读取时合并出来的只读展示（§7.2），落行会随身份变更产生脏数据。
- 唯一约束 `uk_app_access_scope_appId_type_targetId`。索引除 `appId` 外，必须支持按 `type + targetId` **反查**：首页「我的应用」要一次查出「我是所有者的」+「我在配置名单的」+「范围命中我的」（人员 = 我 / 部门 = 我所在部门 / 角色 = 我拥有的启用角色），三个方向都要走索引，否则应用一多首页就变成全表扫。

移交时**必须更新使用范围**：若旧所有者还没有一条「人员 = 旧所有者」的范围行，就补一条（**幂等**，已存在则不重复插）。同时**删掉新所有者**若已有的「人员 = 新所有者」范围行（他已经是所有者，归入「始终可用」）。加入配置名单时同样删掉这个人的人员范围行。旧所有者因此变成普通使用用户；之后**有配置权的人**可以删掉补给他的那条。

**删除应用**：连带删掉这两张表里属于该应用的行。现有 `deleteApp` 只删应用自己，实现时要补上。

流程任务、实例仍按流程规格，不在权限表里复制「谁能批」。

## 12. 接口怎么判（实现对照）

**进应用、看目录、用表单（【添加数据】/【数据管理】）**

1. 未登录 → 和现在一样。
2. 应用不存在 → 不存在。
3. 当前用户不是所有者，且不在配置名单，且使用范围没命中（人员 = 自己 / 所在部门 / 所拥有的启用角色）→ 当作应用不存在。
4. 第 3 步过了就能进应用，也能用表单（【添加数据】、【数据管理】）。所有者、配置名单、使用范围命中，三者任一即可。这就是 **「能使用」**：应用所有者、配置者、使用范围内的人。

**读字典（填报、数据管理回显标签）**

- 按 **「能使用」** 放行，不要按所有者、也不要按配置权。研发部的人打开【请假单】的【添加数据】，下拉要能读到「事假」这种中文，不能因为字典接口还在查是不是所有者而变成空标签或 code。
- 现有 `apps/:appId/dictionaries` 以及按编码取项，把 `requireOwnedApp` 换成「能使用」。
- **改字典**（应用后台「字典管理」里新增、改名、停用、删项）仍按配置权：所有者或配置名单。只有使用权的人进不了应用后台，直接调写接口也当作应用不存在。
- 没有使用权的审批人不能走这条接口，仍按 §8.2 待办抽屉那条按任务放行的读取。

**设计、应用后台、改目录结构、改配置名单、改使用范围、删除表单、转换表单类型**

- 所有者或配置名单上的人。
- 否则当作应用不存在。
- 删除表单属于配置权（§6.3），但界面必须写明会连带删掉该表全部填报数据。
- 转换表单类型的接口（`PATCH /api/apps/:appId/forms/:formId/kind`，流程规格 §17）同样按设计级判：所有者或配置名单。只接受普通 → 流程并回填；已经是流程表单或想改回普通，业务上拒绝。**不要因此抬成「只有所有者能做」**——它改的是这张表的设计属性，和删表单同级。

**删除应用、应用内移交所有者**

- 只有当前所有者。配置名单上的人不行。

**管理后台移交（所有者已停用）**

- 调用人必须拥有启用中的 `system_admin` 角色。
- 该应用当前所有者必须已停用。所有者还在启用 → 拒绝，让他自己进应用后台交。
- 新主人必须是启用中的人。
- 做成管理后台自己的接口，不要复用应用内那条「只有所有者能调」的移交。成功后的名单、使用范围变化与 §5.1 相同。
- 这条接口不能顺便返回表单、数据、字典。

**首页「我的应用」**

- 我是所有者，或在配置名单，或使用范围命中。

**首页待办三个列表、打开抽屉、通过/驳回/撤回/再次提交**

- 不走上面「进应用」第 3 步。
- 按流程规格：任务处理人或发起人。这里**不包括**异常重试（重试单独一条，审批人不能点）。
- 发起人**即使已经失去该应用的使用权**，仍按发起人放行他在途单据的这些操作（§8.1）；但「已通过」只读，改正式数据要能进应用走数据管理，改完重新走审批。
- 应用内待办列表：人必须已经能进这个应用，并且只查当前应用。

**异常单据的重试**（与流程规格 §16.5 同一条，不要写成「管理员」）

- **能点**：发起人（首页「我发起的」，没使用权也能点）；该应用的所有者 / 配置名单上的人（要能进应用，在数据管理打开这条异常单据后点「重试」）。
- **不能点**：审批人；管理后台的系统管理员（他打不开应用，也不走这条接口）。
- 接口：`POST /api/workflow/instances/:instanceId/retry`。

**人员停用**：账号停用后，平台层每个请求就会被拦住（`server/src/auth/auth.service.ts:112-113` 直接抛「账号已停用」），所以配置权、使用权都天然立刻失效，**不需要在应用层再做一遍**。真正要补的是**别人看这条单据时**的表现：审批人被停用后，他自己根本登录不了，不存在「他打开待办」的场景；发起人、所有者在抽屉的进度里应看到「审批人已停用」，并且这条单会卡住没人能批。本期没有转办（流程规格 §19），出路是**发起人**，或该应用的所有者 / 配置名单上的人，对该实例点**重试**，重新解析审批人（流程规格 §16.5 要把「审批人全部停用」列为异常来源之一）。

**所有者账号停用**：所有者登不进去，配置名单上的人仍能改表、填表、点异常重试，但**不能移交、不能删应用**。换主人走 §5.2：系统管理员在管理后台只做移交，仍然打不开这个应用。不做「配置成员替所有者移交」，也不做系统管理员进应用看数据。

### 12.1 实现约定

- **一个判定入口**：把「所有者 / 配置名单 / 使用范围」三件事收进一个访问判定服务（如 `AppAccessService.canUse(userId, appId)`、`canConfigure(userId, appId)`），替换现有散在各处的 `requireOwnedApp`（`server/src/application/application.service.ts:376-382`）。同一次请求内**缓存判定结果**，否则一个页面几个接口会各查一遍四张表。
- **判定用角色 id，不要复用登录态里的 roleCodes**：`getPrincipal` 返回的是 `roleCodes`，且已经过滤掉停用角色（`auth.service.ts:132-135`）；使用范围存的是角色 **id**。要自己查 `user_role` 关联 `role` 且 `role.status = 'active'` 拿 id 再比。
- **部门 / 角色 / 人员停用或删除**：范围行保留但不命中（§7.2）。判定时要带上 `department.status = 'active'`、`role.status = 'active'`，人员范围还要人还在且账号启用；不要只比 id。
- 一人一个部门（`user_department` 对 `userId` 有唯一索引），按部门命中时只需比这一个部门，不含下级部门。没分配部门的人不被任何部门范围命中。
- **读字典用 `canUse`，写字典用 `canConfigure`。** 不要把整组字典接口都抬成配置权，也不要只留给所有者。
- **填报创建人 / 更新人写当前登录人**，不要再写应用 `ownerId`（§9）。流程实例的发起人也是提交当时的当前用户，两处是同一个人。

## 14. 验收

1. **刚建完**：A 建了【人事】。B 首页【我的应用】没有【人事】，改网址也进不去。A 能设计、能填。A 打开【配置权限】，名单只有 A 一行、标「所有者」、没有移除按钮；打开【使用范围】，顶部「始终可用（不可移除）」里是 A，下面的范围条目为空。
2. **只加配置、不开放范围**：A 用「部门经理」角色找出 B、C，只勾了 B 加入【配置权限】。名单变成两行：A（所有者）、B。B 首页能看到【人事】，能进应用后台、能改表单，也能打开【添加数据】、【数据管理】。C 首页没有【人事】。D 后来也当上部门经理，**不能**配置，也**不能**使用。
3. **配【使用范围】**：A 加一条「部门 = 研发部」。研发部的人首页出现【人事】，能打开【请假单】的【添加数据】，打不开【表单设计】。把人调出研发部后，他**下一次请求**就进不去（不用重登、不用等第二天）。
4. **【移交所有者】**：A 把所有者交给 E。确认后 A 被送到项目首页，立刻不能进应用后台、不能改表单；【配置权限】名单第一行变成 E（标「所有者」），A 不在名单里，E 也不作为普通成员出现第二行。【使用范围】里多了一条「人员 = A」。A 首页还有【人事】、还能打开【添加数据】。E 或仍在配置名单里的 B 把「人员 = A」去掉、且没有别的部门/角色盖住 A 之后，A 首页不再有【人事】。所有者始终只有 E 一个人。B 还能配、还能删表单、还能改【使用范围】，但不能【移交所有者】、不能【删除应用】。
5. **待办**：【请假单】审批人是 F，F 不在【使用范围】、也不在配置名单。F 首页没有【人事】。F 在【我的待办】点开卡片，按该节点的字段权限看这一条（隐藏的字段看不到），字典显示中文，并能【通过】/【驳回】。
6. **应用内待办**：E 能进【人事】，左侧【我的待办】只出现【人事】的单。
7. **管理后台管理员 G 不是【人事】的使用/配置**：G 能管人，首页没有【人事】。
8. **【表单发布】关掉【删除】**：有使用权的人（含所有者）【数据管理】里没有【删除】。
9. **移除配置**：E 把 B 从【配置权限】移除，且【使用范围】没有覆盖 B → 确认框先提示「他将同时失去使用权」；确认后 B 首页不再有【人事】，改网址进来提示应用不存在。若【使用范围】里有「部门 = 研发部」且 B 属于研发部 → B 仍能进【人事】打开【添加数据】、【数据管理】，但打不开【表单设计】和应用后台。
10. **部门停用与恢复**：把「研发部」停用 → 靠这条范围进来的人首页立刻没有【人事】；【使用范围】那条显示「研发部（已停用，当前不生效）」。把部门恢复启用 → 这些人自动又能进，**不需要重新配范围**。
11. **移交给原配置名单上的人，再交出去（方案 A）**：A 点【移交所有者】交给 B（B 原本在配置名单里）→ 名单第一行是 B 并标「所有者」，B 的普通成员那一行从库里删掉，不再出现第二行，也没有「移除所有者」的按钮。B 再点【移交所有者】交给 C → 确认后 B 被送到首页；名单第一行变成 C；【使用范围】多了一条「人员 = B」。B 还能进【人事】打开【添加数据】，但打不开【表单设计】和应用后台，直接调配置接口也当作应用不存在。库里没有 B 的配置行。
12. **旧所有者失去使用权后的在途单据**：A 移交前【提交】了一张审批中的【请假单】，E 把【使用范围】里「人员 = A」删掉 → A 首页没有【人事】、进不去应用、看不到【请假单】的【数据管理】；但首页【我发起的】里这张单还在，A 能打开、能【撤回】、能改完【再次提交】。另一张**已通过**的单，A 只能只读看，改不了（进不了【数据管理】）。
13. **审批人被停用**：把部门经理 F 的账号停用 → F 登录不了（提示账号已停用）。发起人在抽屉进度里看到「审批人已停用」，这条单卡住没人能批。发起人在首页【我发起的】能点【重试】；E（所有者）进【请假单】的【数据管理】，打开这条异常单据也能点【重试】→ 重新解析审批人，另一位在职经理收到待办。审批人不能点；系统管理员 G 也不能点。
14. **配置权能删表单、不能移交和删应用**：B（在配置名单）在表单树里删除【请假单】时，确认框写明「将同时删除该表单已填报的 N 条数据，不可恢复」；删除后该表填报数据一并没了。B 在应用后台看不到【移交所有者】、【删除应用】，直接调接口也被拒。
15. **无使用权审批人的抽屉走流程接口**：F 不在【使用范围】，点开【我的待办】卡片后，「请假类型」显示「事假」而不是 code；节点若允许改「选择数据」，弹窗能列出源表已通过的记录；本条已有图片能看。这些请求都走 `/api/workflow/...`，直接调 `GET /apps/:appId/dictionaries` 或 `records/query` 当作应用不存在。F 点【通过】/【驳回】走待办接口，不走 `PATCH /records`。
16. **转表单类型看配置权**：B（在配置名单）在表单树上对【加班单】（普通表单）点【转为流程表单】→ 确认框写清已有数据将记为已通过；转成功后顶栏出现【流程设计】。【请假单】已经是流程表单，菜单里**没有**「转为普通表单」，直接调接口改回普通也被拒。研发部的 H 只有使用权 → 表单树节点菜单里没有【转为流程表单】，直接调 `PATCH /api/apps/:appId/forms/:formId/kind` 也被拒（当作应用不存在）。
17. **已通过只有原发起人能在【数据管理】里改**：A 还能进【人事】。首页【我发起的】里 A 自己那张已通过的【请假单】只读，没有【提交】。A 进【请假单】的【数据管理】，【表单发布】里【编辑】开着，打开这行改事由后点【提交】→ 状态变回审批中，按当前已发布流程走。E（所有者、不是这张单的发起人）打开 A 的那行只能看，没有【编辑】。【表单发布】里【编辑】关着则 A 也没有【编辑】。A 若已被移出【使用范围】，【数据管理】进不去，已通过只能在【我发起的】里看。
18. **所有者停用后系统管理员仅做移交**：把 E 的账号停用 → E 登录不了。B（仍在配置名单）还能进【人事】、还能改表单，但应用后台看不到【移交所有者】、【删除应用】，直接调这两条接口也被拒。系统管理员 G 首页仍然没有【人事】，改网址也进不去、看不到【请假单】数据。G 进管理后台 → 人员 → 打开已停用的 E → 看到【人事】→ 点移交，交给启用中的 K → 成功后 K 成为所有者，首页出现【人事】。G 自己首页仍然没有【人事】（除非他把应用交给了自己）。只有 `admin.access`、没有系统管理员角色的人，人员页上看不到移交。
19. **【使用范围】不能加停用账号；没部门的人靠角色或点名**：添加人员时，停用的账号不出现、勾了也写不进去。没分配部门的 I，加「部门 = 研发部」之后首页没有【人事】；给 I 一个启用中的「部门经理」角色并加「角色 = 部门经理」，或直接加「人员 = I」，首页出现【人事】。
20. **已删除范围回显**：把已加进【使用范围】的「研发部」删掉（管理后台删除部门）→ 这条仍在，显示「研发部（已删除，当前不生效）」，并提示去修改；靠它进来的人进不去。若名字已经读不到，显示「部门（id:该部门id，已删除，当前不生效）」。
21. **配置名单上的人被停用**：把 B 停用 → B 登录不了。【配置权限】里 B 那一行标「已停用」，仍有移除按钮。E 点移除，确认后名单里不再有 B。
22. **有配置权的人能改名单和范围，也可以移除自己**：B（在配置名单）打开【使用范围】，能删「人员 = A」，效果和 E 去删一样。B 打开【配置权限】，能把自己那一行移除；确认后 B 回到项目首页，打不开应用后台。【使用范围】若还有「部门 = 研发部」且 B 在研发部，B 首页仍有【人事】，但只能打开【添加数据】，不能再进后台。
23. **填报创建人是当前用户**：研发部的 H 在【请假单】的【添加数据】里填一张并【保存】。【数据管理】这行的创建人是 H，不是所有者 E。E 再改这行，更新人是 E，创建人仍是 H。
24. **有使用权的人读字典**：研发部的 H 只有使用权。打开【请假单】的【添加数据】，「请假类型」下拉能看到「事假」「病假」，不是空的也不是 code。H 进不了【字典管理】；直接调新增字典的接口被拒（当作应用不存在）。

| 发起人失去使用权后 | **已拍板**：仍可经首页「我发起的」操作在途单据（草稿/审批中/已驳回/异常）；不能进应用、不能进数据管理；已通过只读；**不能在首页删草稿**（没有删除入口） |
| 草稿怎么删 | **已拍板**：发布页「删除」开着才能删，只走数据管理。首页「我发起的」没有删除入口。失权后也不能在首页删 |
| 权限表列名怎么写 | **已拍板**：按项目现有风格。表名单数下划线，列名驼峰（`appId` / `userId`）。普通索引 `IDX_`，唯一约束 `uk_` |
| 「我发起的」列不列异常 | **已拍板**：列。点开可以重试 |
| 异常单据谁能点「重试」 | **已拍板**：以 §12 与流程规格为准。发起人（首页就能点，没使用权也可以）；能进应用的所有者 / 配置名单上的人（数据管理打开这条异常单据后点）。审批人不能点；系统管理员不能点。不要写成「管理员或发起人」 |
| 已通过后还要改 | **已拍板**：只有原发起人能在数据管理里改（发布页「编辑」开着），别人只能看。「我发起的」里只读。改完用当前已发布版本重新审批（流程规格 §11） |
| 加入名单 / 升为所有者时的人员范围行 | **已拍板**：删掉「人员 = 他」那一条，避免和「始终可用」重复 |
| 填报的创建人是谁 | **已拍板**：当前填报的登录用户，不是应用所有者。更新人同样是当前登录人 |
| 读字典按什么鉴权 | **已拍板**：按「能使用」（所有者、配置者、使用范围内的人）。改字典仍按配置权。没有使用权的审批人走待办那条按任务读取（§8.2） |
| 待办抽屉的读和写走哪 | **已拍板**：全部走 `/api/workflow/...`，按这条任务 / 实例授权。打开一次带齐结构、字典、本条数据；选记录 / 联动 / 文件另开窄接口。`/apps/:appId/...` 不为待办开例外，也不给待办开放 `PATCH /records`（§8.2） |
| 首页再存草稿 / 再交怎么保存 | **已拍板**：鉴权走流程实例接口（只认发起人）；保存走与应用 records 同一套，不要在流程服务里直接写 Mongo。工作台 / 数据管理仍先判能使用。两扇门，一间库房（流程规格 §17） |
| 谁能改配置名单、使用范围 | **已拍板**：有配置权的人（所有者或配置名单上的人）。配置成员可以移除其他普通成员，也可以移除自己；所有者那一行不能移除 |
| 从配置名单移除一个人 | 同时失去使用权，除非使用范围覆盖他；移除时提示 |
| 配置权是否随部门/角色自动变 | 否，只保留添加当时勾上的人 |
| 使用范围是否随部门/角色自动变 | 是 |
| 使用范围能不能加停用账号 | **已拍板**：不能 |
| 没分配部门的人怎么进使用范围 | **已拍板**：部门范围盖不住。靠他们有的角色，或直接按人员点名 |
| 部门 / 角色 / 人员被停用或删除 | **已拍板**：范围行保留但不命中，恢复启用后自动生效。停用标「已停用，当前不生效」；已删除标「研发部（已删除，当前不生效）」，并提示去修改；名字读不到则「部门（id:xxxxx，已删除，当前不生效）」 |
| 配置名单上的人后来停用 | **已拍板**：丧失配置权（人也登不进去）；名单行标「已停用」，可以移除，移除后不再显示 |
| 使用范围包不包括下级部门 | 不包括 |
| 移交后配置名单里有谁 | **已拍板**：既没有旧所有者，也没有新所有者。新所有者若移交前在名单里，删掉那一行；不要给旧所有者加名单行 |
| 移交给本来就在名单里的人，再交出去 | **已拍板（方案 A）**：升为所有者时删掉他的配置行。他再交出去后就是普通人，只靠自动补的「人员 = 他」使用范围，不再能配置。不要留着那一行 |
| 移交后旧所有者 | **已拍板**：写成普通使用用户，使用范围必须补「人员 = 旧所有者」（已有则不重复）；之后有配置权的人可再移除 |
| 能配置能否使用 | 能。配置名单上的人同时有使用权，不必再写入使用范围 |
| 配置名单上的人首页能否看到应用 | 能 |
| 待办要不要使用权 | 不要；看的是那一条 |
| 审批人被停用导致单据卡死 | 本期没有转办；出路同上一条「重试」，重新解析审批人 |
| 所有者账号停用 | **已拍板**：配置名单上的人仍能改表、用表，但不能移交、不能删应用。换主人：系统管理员在管理后台仅做移交，打不开应用、看不到数据 |
| 按表「谁可以」 | 第 3 期再做 |
| 菜单单独配置 | 不做 |
